# Учебник по созданию модов EveJS (взгляд автора)

> Для тех, кто **хочет сделать мод**: от нуля до мода, который можно установить с рынка модов — всего **8 шагов**.
> По ходу дела **не нужно менять ни одного файла сервера** — моды подключаются через loader.

**Что понадобится**: Windows 10+, сервер EveJS (0.12.8 или новее), лаунчер EvEJS 0.1.20+ и аккаунт GitHub.

# Часть 1: подготовка (один раз)

## Шаг 1 ✅ Проверить окружение

1. Откройте лаунчер → **Самопроверка среды**: 9 пунктов (Node.js / зависимости / путь к клиенту и т. д.). Сначала устраните красные.
2. Проверьте корень сервера EveJS (содержит `server/`, `config/`). В лаунчере → **центр настроек** показан текущий путь.
3. Убедитесь, что существует папка **`mods/`**. Если нет — Моды / плагины → **создать mods/ автоматически**.

🟨 **Внимание**: папка модов строго `<корень EveJS>/mods/<ID мода>/`. **Не переносите** её в другое место и не переименовывайте в не-ASCII символы.

---

## Шаг 2 ✅ Создать идентичность автора (доказательство того, «кто вы»)

Моды / плагины → вверху **настройка токена** (идентичность автора и токен GitHub в одном окне):

1. **При первом открытии пара ключей Ed25519 создаётся автоматически** (нажимать ничего не нужно)
2. Измените **отображаемое имя** (имя для людей, например «Командир») → **сохранить отображаемое имя**
3. Нажмите **экспортировать ключ** → сохраните файл `.eve-key` **в надёжном месте** (флешка / менеджер паролей)
4. При смене компьютера: на новой машине нажмите **импортировать ключ** и выберите этот `.eve-key` — идентичность восстановится
5. Кнопка **папка ключей** сразу открывает каталог с закрытым ключом (`_launcher/data/mod-keys/`)

Вы получите три вещи:

| Вещь | Описание | Нужно ли хранить |
| --- | --- | --- |
| **ID автора** (`au-...`) | Записывается в манифест мода и означает «этот мод сделали вы» | Записывается в манифест автоматически |
| **Отпечаток ключа** (`keyId`, 12 символов) | Нужен для проверки подписи | Записывается в манифест автоматически |
| **Файл `.eve-key`** | Внутри — **закрытый ключ** | 🟥 **Обязательно сохранить** |

🟥 **Опасно**:
- **`.eve-key` — это ваша личность.** Потеряете → вы **больше никогда не подпишете обновление** (старые пользователи увидят «подпись не прошла»); утечёт → кто-то сможет публиковать от вашего имени.
- **Никогда** не коммитьте `.eve-key` или `_launcher/data/mod-keys/*.key` на GitHub, не передавайте их другим и не кладите в ZIP.

🟩 **Рекомендуется**: при смене компьютера верните `.eve-key` через «импортировать ключ» — идентичность восстановится.

---

## Шаг 3 ✅ Создать токен GitHub (нужен и для публикации, и для подачи)

Лаунчер работает с GitHub за вас: при **публикации** он пишет файлы в ваш собственный репозиторий, создаёт Release и загружает ZIP; при **заявке на включение** он форкает репозиторий индекса `diguo520/EVEjs-mods` (принадлежит мейнтейнеру) и открывает PR. Один **токен classic** покрывает оба случая.

### 3.1 Открыть нужную страницу 🟨

```
GitHub, аватар справа вверху → Settings → в левой колонке в самом низу Developer settings
  → Personal access tokens → Tokens (classic) → Generate new token (classic)
```

Нажимайте по картинке ниже (номера соответствуют красным кругам на странице):

![Страница токена classic на GitHub: ① Tokens (classic) ② Generate new token (classic) ③ Note ④ Expiration ⑤ отметить repo](./github-token-classic.png)

| № | Куда нажать / что ввести |
| --- | --- |
| ① | Левая колонка **Tokens (classic)** — не Fine-grained tokens выше |
| ② | **Generate new token** → **Generate new token (classic)** |
| ③ | **Note**: любой текст, например `evejs-launcher` |
| ④ | **Expiration**: рекомендуется 90 дней (по истечении создать заново) |
| ⑤ | В **Select scopes** отметить **repo** (`public_repo` — подпункт; отметив repo, вы его получаете) |

🟥 **Не используйте токен fine-grained**: его Repository access позволяет выбирать только репозитории, где у вас уже есть права, но не репозиторий индекса `EVEjs-mods`, принадлежащий мейнтейнеру; а для форка и PR нужны права записи именно в нём. С токеном fine-grained подача гарантированно упадёт с `403 Resource not accessible by personal access token`.

### 3.2 Заполнить основные данные

| Поле | Что ввести |
| --- | --- |
| Note | Любой текст, например `evejs-launcher` |
| Expiration | 90 дней или свой срок (по истечении создать заново) |

### 3.3 Отметить scope (главное) 🟨

| scope | Отмечать? | Зачем |
| --- | --- | --- |
| **public_repo** | 🟩 Обязательно | Чтение и запись публичных репозиториев: Release, загрузка ZIP, форк, PR — всё на нём |
| **repo** | 🟨 Рекомендуется | Включает public_repo; нужен, если хотите, чтобы лаунчер сам создавал репозитории и управлял приватными |

### 3.4 Сгенерировать и скопировать

Нажмите **Generate token** → скопируйте строку `ghp_...` (🟨 **показывается один раз**; закроете страницу — больше не увидите).

### 3.5 Ввести в лаунчер

Моды / плагины → **настройка токена** → найдите поле токена GitHub → вставьте → **сохранить** (хранится локально в зашифрованном виде; права проверяются автоматически после сохранения) → проверка пройдена.

> 🟦 **Почему classic?** Репозиторий индекса принадлежит мейнтейнеру, и токен fine-grained до него не достаёт. Только те, кого добавили **соавтором репозитория индекса**, могут использовать fine-grained: выберите `EVEJS-mods` в Repository access и включите **Contents = Read and write** и **Pull requests = Read and write**.

🟨 **Внимание**: после изменения scope или пересоздания токена **вставьте и сохраните новый токен заново**.

# Часть 2: делаем мод

## Шаг 4 ✅ Создать мод (сгенерировать каркас)

Моды / плагины → **создать мод**, заполните форму:

| Поле | Обязательно | Описание |
| --- | --- | --- |
| Шаблон | ✅ | `Welcome Broadcast (Example)` (пример с приветствием при входе) / `Blank Skeleton` (пустой каркас). 🟩 В первый раз лучше прогнать пример |
| Имя мода | ✅ | Имя, которое видят игроки |
| ID (id / имя папки) | 🟩 | Генерируется из имени автоматически; допустимы только `a-z 0-9 - _ .`; после создания **больше не меняйте** |
| Версия | ✅ | По умолчанию `1.0.0`; для новой версии нужно **увеличивать** (см. шаг 8) |
| Категория | ✅ | Геймплей / Экономика / ИИ / Графика / Инструменты (по ней фильтрует рынок) |
| Теги | ⭕ | Через запятую, например `чат, новичок` |
| Краткое описание | 🟩 | Одно предложение, показывается на карточке рынка |
| Подробное описание / ключевые пункты | ⭕ | Попадут в README вашего мода |
| ID связанных модов | ⭕ | С какими модами он связан, через запятую или пробел |
| Опции сборки | — | ☑ перезапустить сервер (по умолчанию включено), ☑ включить сразу после создания (включено), ☑ подписать сразу после создания (включено) |

После нажатия **Создать** в папке `mods/` появится:

```
mods/<ID вашего мода>/
├─ evejs-launcher.mod.json    ← манифест (идентичность, версия, категория, зависимости)
├─ loader.js                  ← логика, которую вы пишете
├─ README.md                  ← создаётся из «подробного описания»
└─ CHANGELOG.md               ← история версий
```

🟨 Только если **снять** галочку «включить сразу после создания», `loader.js` будет создан как `loader.js.disabled` (по умолчанию галочка стоит, поэтому по умолчанию это загружаемый `loader.js`). Переключить потом можно в переключателе на вкладке **Установленные** — он просто переименовывает файл.

🟨 **Обязательные поля манифеста** (лаунчер их проверяет; если чего-то нет, будет «проверка манифеста не прошла»):

```
schemaVersion: 3                       ← должно быть 3
id / displayName / version             ← ID / имя / версия
kind: "loader"                         ← реально включить можно только loader
restart: "game_server"                 ← none | client | game_server | launcher
activation.strategy: "loader_rename"   ← обязательно это значение
в папке должен быть loader.js или loader.js.disabled
```

## Шаг 5 ✅ Написать свою логику (`loader.js`)

Откройте `mods/<ID вашего мода>/loader.js` — каркас уже внутри: 🟩 **этот каркас и есть рабочий минимальный пример** (игрок через 10 секунд после входа получает сообщение в локальном чате). Просто правьте его.

🟥 **Четыре жёстких правила** (все есть в каркасе; удалите любое — получите проблему):

| Правило | Почему |
| --- | --- |
| `setImmediate` + проверка входа (`process.env.EVEJS_GAMESTORE_OWNER_ROLE === "world"`, либо точка входа — `index.js`) | `NODE_OPTIONS` наследуется от npm до сервера послойно, и каждый процесс-обёртка загружает ваш файл; без проверки вы будете работать не в том процессе |
| **Не `require`-ьте крупные модули сервера напрямую** (`chatHub` поднимает около 456 МБ / 645 модулей) | Дождитесь появления в `require.cache` и тогда берите ссылку: попадание в кэш, ноль лишней памяти |
| `timer.unref()` | Чтобы таймер не удерживал процесс от завершения |
| Использовать `globalThis.__xxx` для «установить один раз» | loader загружается несколько раз, иначе сообщения дублируются, а слушатели накапливаются |

🟨 **Правило путей (самая частая ловушка)**: внутри loader `require("./src/...")` разрешается **относительно ВАШЕЙ папки мода**, а **не** корня сервера — так вы получите `MODULE_NOT_FOUND`. Правильно сначала вычислить корень сервера:

```js
const path = require("path");
const serverRoot = path.resolve(__dirname, "..", "..", "server");
const hubPath = path.join(serverRoot, "src", "services", "chat", "chatHub.js");
// 🟨 Не require-ьте здесь напрямую — дождитесь, пока сервер сам его загрузит; полный пример в приложении B
```

🟨 **Атрибуты сессии**: собственные атрибуты чат-сессии **не синхронизируются автоматически**; прямое чтение и запись могут «молча не сработать». Используйте интерфейсы `chatHub` / `sessionRegistry`.

🟩 Моды, которым нужно **править исходники сервера** (а не только вызывать API), смотрите в **приложении G** — не вешайте собственный хук на `Module.prototype._compile`.

## Шаг 6 🟩 Локальный тест

1. Моды / плагины → **Установленные** → найдите свой мод → включите переключатель (или поставьте галочку «включить сразу» при создании)
2. Лаунчер → консоль → **запуск в один клик** (поднимает основной сервер и сервис рынка)
3. Зайдите в игру и проверьте эффект
4. При проблемах смотрите два лога:
   - Лаунчер → **лог сервера** (фильтры по Система / основной сервер / сервис рынка / клиент и по INFO/WARN/ERROR)
   - Вывод консоли сервера (виден в лаунчере)
5. 🟩 **Проверить «загрузилось ли вообще и сколько это заняло»**: ищите в выводе сервера `[EveJS-MOD]`:
   - `loader готов <ваш мод> 3ms` — ваш loader загружен; `loader сбой ... :: <причина>` значит, что не загрузился
   - `loaders-done total=14 failed=0 ms=1086` — общее время загрузки всех модов
   - `<файл> внедрено N слоёв (A -> B байт)` — патч шины сработал
   - `<id> патч не удался, результат предыдущего слоя сохранён: <причина>` — этот слой пропущен (**не влияет** на другие моды)

   🟨 Подробности по каждому процессу и каждому слою также пишутся в `_launcher/logs/mod-load-report.json` — смотрите туда, когда нужно понять, «кто изменил файл».

### 🔧 Быстрая шпаргалка по ошибкам

| Симптом | Наиболее вероятная причина |
| --- | --- |
| В списке «нет loader.js» | Файл удалён или переименован |
| Переключатель включился и сам выключился | Проверка манифеста не прошла / подпись изменена → смотрите красную пометку на карточке |
| В логе нет «загрузка мода» | Мод **отключён** или пропущен из-за конфликта |
| В логе `MODULE_NOT_FOUND` | `require("./src/...")` был разрешён от корня сервера — на самом деле он относителен вашей папки мода (см. шаг 5) |
| В игре нет эффекта и в логе нет ошибок | Логика вышла через `return` до проверки «установить один раз», либо путь в `require` ошибочный |
| Память Node резко растёт | Загружен крупный модуль сервера через `require` (ловушка 2 из шага 5) |

# Часть 3: публикация на рынке

> **Публикация — это одно нажатие**: лаунчер подряд делает «переподписать → упаковать ZIP → запушить в ваш репозиторий (создать репозиторий, создать Release, загрузить ZIP) → открыть PR на проверку версии в репозиторий индекса», а вы следите только за прогрессом.
> PR в репозиторий индекса открывается **с каждой версией** — только после слияния рынок переключается на новую версию.

## Шаг 7 ✅ Опубликовать и выложить на рынок (одно нажатие)

Моды / плагины → **опубликовать мод** (кнопки «отправить на проверку / отправить заново» на карточке «Мои моды» открывают то же окно):

1. **Выбрать мод**: в списке **только ваши собственные моды** (чужие не показываются, чтобы не отправить по ошибке)
2. Укажите **номер версии** и **описание изменений** (описание попадёт в индекс и PR — пишите простыми словами)
3. Проверьте **категорию / теги**; **адрес исходников / проекта** ⭕ необязательно (например `https://github.com/вы/ваш-мод`), **прямая ссылка на GitHub Releases** ⭕ оставьте пустой (правильный адрес сгенерируется при публикации)
4. Отметьте три заявления (авторская работа / нет вредоносного кода / правила и условия прочитаны)
5. Нажмите **Опубликовать**

Кнопка «Опубликовать» станет активной только при выполнении условий сверху окна: **отображаемое имя** (шаг 2), **токен GitHub** (шаг 3), **30 минут между двумя отправками одного мода**, **60 секунд между публикациями**. Чего не хватает — та строка подсветится жёлтым и даст ссылку на исправление.

### Четыре этапа в прогрессе

| Этап | Что делает | Где |
| --- | --- | --- |
| Локальная упаковка | Переподписать → упаковать ZIP → посчитать SHA256 → создать манифест для рынка | **Только локально**: без сети и токена |
| Подготовка вашего репозитория | Создаёт публичный репозиторий, если его нет | Ваш GitHub |
| Публикация Release и загрузка пакета | Записывает `evejs-mod.json` (его читает рынок) → создаёт Release (tag = `v<версия>`) → загружает `<id>-<версия>.zip` | Ваш GitHub |
| Открытие PR на проверку версии | PR в репозиторий индекса: в первый раз дополнительно `sources.json` (регистрация), далее с каждой версией только `mods/<id>.json` | Репозиторий индекса `diguo520/EVEjs-mods` |

Артефакты и журнал:

| Артефакт | Где |
| --- | --- |
| ZIP-пакет | `_launcher/temp/export-<id>-<version>.zip` (тот же файл загружен в ваш Release) |
| Журнал отправок | `_launcher/data/my-submissions.json` |

🟨 **Изменили код — нажмите «Опубликовать» заново**: как только содержимое меняется, подпись становится недействительной; лаунчер заново подпишет, упакует и отправит новую версию.

### 🔧 Частые ошибки на этом шаге

| Ошибка | Причина | Как исправить |
| --- | --- | --- |
| 🟥 `403 Resource not accessible by personal access token` | Токен fine-grained, либо classic без public_repo | Используйте токен classic с **public_repo**; репозиторий индекса принадлежит мейнтейнеру, токен fine-grained до него не достаёт. Если вас уже добавили соавтором репозитория индекса: fine-grained с `EVEjs-mods` + Contents / Pull requests = Read and write |
| 🟥 `net::ERR_INVALID_ARGUMENT` | Баг загрузки ZIP в старых лаунчерах | Обновитесь до **0.1.20+** |
| 🟥 `404` | Репозитория нет или токен его не покрывает | Проверьте написание owner/repo; используйте classic-токен (public_repo / repo) |
| 🟥 `токен GitHub не заполнен` | Токен не сохранён | Вернитесь к шагу 3.5 |

🟩 **После успеха**: в окне появятся адрес репозитория и адрес Release (можно открыть и убедиться, что ZIP на месте); карточка переходит в **на проверке**.

### Проверка и слияние

- Мейнтейнер проверяет ваш мод в PR (поля манифеста, категория, расположение ZIP, номер версии и т. д.)
- **Принято (слито)**: CI индекса сразу пересобирается, рынок переходит на вашу версию, её находят все лаунчеры
- **Не принято**: мейнтейнер отвечает в PR, а в **Моих модах** карточка становится красной и указывает **причину отказа**

🟨 **Один и тот же мод можно отправлять не чаще раза в 30 минут**: частые нажатия продублируют Release и будут обновлять один и тот же PR; окно показывает оставшееся время, а кнопка до этого серая.

🟦 После отправки лаунчер **проверяет PR ещё раз**, убеждаясь, что он действительно открыт, и записывает номер и статус в журнал:
карточка в «Моих модах» показывает `на проверке / слито / PR закрыт` (этот статус перепроверяется не чаще раза в 30 минут, чтобы не дёргать GitHub без нужды).

# Приложение B: рабочий каркас loader

Это **сокращённая версия** каркаса из «создать мод» — все четыре жёстких правила на месте, правьте и пользуйтесь (полная версия с комментариями лежит в `mods/<ID вашего мода>/loader.js`):

```js
"use strict";
const path = require("path");

const TAG = "[мой-мод]";
const MOD_ID = "my-mod";
const POLL_MS = 3000;
const GRACE_MS = 10000;                      // столько ждать после входа: сессия должна сначала подготовиться
const MESSAGE = "С возвращением, пилот!";

// Откройте этот блок, если нужно менять исходники сервера (новый механизм: сообщить шине, только дописывать):
//   target —— относительно корня EveJS, прямые слэши
//   marker —— уникальная метка; если уже есть, шина пропускает слой (идемпотентно)
//   slot   —— порядок нескольких слоёв для одного файла, меньше — раньше (рекомендуются кратные 10)
//   append —— только дописываемый код, никогда не переписывать файл целиком
const SOURCE_PATCH = null;
// const SOURCE_PATCH = {
//   target: "server/src/network/tcp/handshake.js",
//   marker: "// my-mod:patch",
//   slot: 40,
//   append: "// my-mod:patch\nconsole.log('[my-mod] patched');",
// };

console.log(TAG + " preload выполнен · pid=" + process.pid);

/** Продолжать только в настоящем процессе сервера (исключая npm / процессы-обёртки) */
function isRealServerProcess() {
  if (process.env.EVEJS_GAMESTORE_OWNER_ROLE === "world") return true;
  const entry = (require.main && require.main.filename) || process.argv[1] || "";
  return /(^|[\\/])index\.js$/i.test(entry);
}

/** Зарегистрировать патч исходников в шине внедрения (🟥 должен выполняться синхронно, см. ниже) */
function registerSourcePatch() {
  if (!SOURCE_PATCH || !SOURCE_PATCH.target) return;
  const bus = globalThis.__evejsMods;
  if (!bus || !(Number(bus.api) >= 1)) {
    console.log(TAG + " старый лаунчер без шины внедрения, патч исходников пропущен");
    return;
  }
  bus.register({
    id: MOD_ID,
    target: SOURCE_PATCH.target,
    marker: SOURCE_PATCH.marker,
    slot: SOURCE_PATCH.slot,
    apply: (source) => source + "\n" + SOURCE_PATCH.append + "\n",
  });
}
// 🟥 Регистрировать синхронно: сервер требует целевые файлы уже при запуске,
//    регистрация внутри setImmediate слишком поздняя (файл уже скомпилирован, и патч не сработает)
registerSourcePatch();

setImmediate(() => {
  if (!isRealServerProcess()) return;
  if (globalThis.__myModStarted) return;      // 🟨 загружается несколько раз: устанавливаем один раз
  globalThis.__myModStarted = true;
  start();
});

function start() {
  // 🟥 require("./src/...") относителен ВАШЕЙ папки мода, а не корня сервера — сначала вычислите корень
  const serverRoot = path.resolve(__dirname, "..", "..", "server");
  const hubPath = path.join(serverRoot, "src", "services", "chat", "chatHub.js");
  const registryPath = path.join(serverRoot, "src", "services", "chat", "sessionRegistry.js");

  // 🟨 Дождитесь, пока сервер сам положит эти два модуля в require.cache, и тогда берите ссылку:
  //    попадание в кэш, ноль лишней памяти, граф модулей на 456 МБ не поднимается заранее
  const timer = setInterval(() => {
    if (!require.cache[require.resolve(hubPath)]) return;
    if (!require.cache[require.resolve(registryPath)]) return;
    clearInterval(timer);
    run(require(require.resolve(hubPath)), require(require.resolve(registryPath)));
  }, 500);
  timer.unref();
}

function run(chatHub, sessionRegistry) {
  const seen = new Set();
  const firstSeenAt = new Map();

  const timer = setInterval(() => {
    let sessions;
    try {
      sessions = sessionRegistry.getSessions() || [];
    } catch {
      return;
    }

    const now = Date.now();
    const online = new Set();

    for (const session of sessions) {
      const characterID = sessionRegistry.resolveSessionCharacterID(session);
      if (!characterID) continue;              // ещё не в игре, ждём следующий круг
      online.add(characterID);
      if (!firstSeenAt.has(characterID)) firstSeenAt.set(characterID, now);
      if (seen.has(characterID)) continue;
      if (now - firstSeenAt.get(characterID) < GRACE_MS) continue;

      try {
        // У некоторых объектов сессии есть только charid в нижнем регистре: дополним, чтобы не было «тихой отправки»
        if (!Number(session.characterID || 0)) session.characterID = characterID;
        chatHub.sendSystemMessage(session, MESSAGE);
        seen.add(characterID);
        console.log(TAG + " сообщение отправлено персонажу " + characterID);
      } catch (error) {
        console.log(TAG + " персонаж " + characterID + " ещё не готов, повторим позже: " + error.message);
      }
    }

    // Убираем вышедших из игры: при следующем входе сработает снова
    for (const id of Array.from(seen)) if (!online.has(id)) seen.delete(id);
    for (const id of Array.from(firstSeenAt.keys())) if (!online.has(id)) firstSeenAt.delete(id);
  }, POLL_MS);
  timer.unref();
}
```

🟨 Использованные выше интерфейсы сервера **проверены на практике**:

| Интерфейс | Назначение |
| --- | --- |
| `sessionRegistry.getSessions()` | Массив онлайн-сессий (🟥 **не** `list()`, такого метода нет) |
| `sessionRegistry.resolveSessionCharacterID(session)` | Возвращает ID персонажа (0, пока он не в игре) |
| `chatHub.sendSystemMessage(session, "сообщение")` | Отправляет системное сообщение в локальный канал этого персонажа |

Интерфейсы могут меняться от версии EveJS — ориентируйтесь на реальные экспорты вашей версии.

# Приложение C: конфликты и порядок загрузки

| Тип | Как возникает | Последствие |
| --- | --- | --- |
| Объявленный конфликт | В манифестах `conflicts` ссылаются друг на друга | Два мода не включатся одновременно |
| Дублирование `id` | У двух манифестов одинаковый `id` | Загрузится только один |
| Общий модуль сервера | Несколько loader ссылаются на один модуль сервера | Могут влиять друг на друга (лаунчер предупредит) |
| Нет зависимости | Мод из `requires` не установлен | Этот мод не загрузится |

🟦 Порядок загрузки: на вкладке **Установленные** перетаскивайте карточки или нажмите кнопку «⤓ в конец» слева сверху на карточке. Список сгруппирован — включённые моды сначала, отключённые после, — и внутри каждой группы ваш порядок: отключать мод и заново сортировать не нужно, при включении он возвращается на место.
🟨 `loadAfter` / `loadBefore` в манифесте **имеют больший приоритет** и корректируют заданный перетаскиванием порядок; сдвинутый мод помечается в панели «Порядок загрузки» как «сдвинуто правилом манифеста».
🟦 Панель «Порядок загрузки» показывает **фактически действующий** порядок, а также моды, которые **не загрузятся** в этот раз (битый манифест / нет зависимости / конфликт / нет loader.js), и объявления порядка **без эффекта** (цель не установлена или отключена, папка из сохранённого порядка исчезла). Изменения вступают в силу после **перезапуска сервера**.

## 🟥 Несколько модов правят один файл сервера (в новом лаунчере есть решение)

Если мод **сам вешает хук на `Module.prototype._compile`**, чтобы менять исходники сервера, при двух модах на одном файле возникает проблема:

- кто первым увидит исходный файл — целиком зависит от порядка загрузки;
- если один проверяет по «sha256 всего файла», он **получит несовпадение**, потому что второй уже дописал содержимое;
- реально наблюдавшаяся картина: `автоматическая добыча` и `автозахват и автоогонь` оба дописывали код в конец `server/src/network/tcp/handshake.js`; внедрённый первым записывал, второй видел другой хеш и **молча отказывался** (ни ошибки, ни эффекта).

🟩 Новый лаунчер даёт для этого **шину внедрения**: моды больше не вешают хуки по отдельности, а через `__evejsMods.register` объявляют «какой файл и что добавить», а шина выстраивает слои по `(slot, порядок регистрации)` — каждый слой видит содержимое, **уже изменённое предыдущим**. Как пользоваться — в **приложении G**.

# Приложение D: структура ZIP и правила импорта

### Структура ZIP (поддерживаются оба, рекомендуется второй способ)

```text
Способ 1: манифест прямо в корне        Способ 2: обёртка одним уровнем папок (рекомендуется)
my-mod.zip                          my-mod.zip
├── evejs-launcher.mod.json          └── my-mod/
├── loader.js.disabled                   ├── evejs-launcher.mod.json
└── README.md                            ├── loader.js.disabled
                                          └── README.md
```

Лаунчер сам находит корень пакета; ZIP с **несколькими** пакетами модов будет отклонён (один импорт за раз).

### Правила, когда кто-то импортирует ваш ZIP

| Правило | Описание |
| --- | --- |
| Место установки | `<корень EveJS>/mods/<id из манифеста>` (недопустимые символы id заменяются на `-`) |
| Начальное состояние | **Принудительно отключён** (`loader.js` возвращается в `loader.js.disabled`), пользователь включает вручную |
| Совпадение имён | В `mods/` уже есть папка с таким именем → импорт отклонён с подсказкой |
| Нет манифеста | В ZIP нет `evejs-launcher.mod.json` → отклонён |

### 🟨 Размер

Страница модов **рекурсивно считает занимаемое место каждого мода**. Упаковывайте только нужные для работы файлы — 🟥 не кладите в ZIP репозиторий исходников, `node_modules`, скриншоты и `.git`.

# Приложение E: как внедряется loader

🟩 **Сейчас (через шину внедрения)**: лаунчер помещает в `NODE_OPTIONS` **одну** строку `--require "<mod-host.js из комплекта лаунчера>"`, а ваш `loader.js` подключает шина в порядке из `_launcher/mods/mod-plan.json`. Поэтому имя папки мода может содержать не-ASCII или пробелы; `[EveJS-MOD] loaders-done total=N failed=0 ms=X` в логе лаунчера — это «сколько миллисекунд заняла загрузка всех модов».

🟨 **Ниже — старый способ «один `--require` на каждый loader»** (сейчас используется только как страховка, если не удалось записать план шины): лаунчер внедряет ваш `loader.js` в процесс сервера через `NODE_OPTIONS=--require ...` Node. Поэтому:

- 🟥 **Обратные слэши съедаются как экранирование** → `C:\mods\x\loader.js` превращается в `C:modsxloader.js`
- 🟨 `NODE_OPTIONS` делится по пробелам, поэтому **пути с пробелами нужно брать в кавычки**

Правильно — «заменить путь на прямые слэши + обернуть в двойные кавычки»; именно так это собирает сам лаунчер (проверено на практике):

```js
const requireArgs = paths.map((p) => '--require "' + p.replace(/\\/g, "/") + '"').join(" ");
```

🟦 Вам **не нужно** собирать это самостоятельно — достаточно знать, что «в папке мода не должно быть не-ASCII и пробелов», чтобы сопоставлять при разборе проблем.

# Приложение G: правка исходников сервера — шина внедрения `__evejsMods.register`

🟨 Этот раздел нужен только модам, которым **обязательно нужно менять исходники сервера**. Моду вроде «приветствие при входе», который лишь вызывает API сервера, достаточно приложения B.

Шину внедряет лаунчер; на стороне мода достаточно объявления в конце файла:

```js
const bus = globalThis.__evejsMods;
if (bus && bus.api >= 1) {
  bus.register({
    id: "ID вашего мода",                           // совпадает с id в манифесте, используется как метка в отчёте
    target: "server/src/network/tcp/handshake.js",  // относительно корня EveJS, прямые слэши
    marker: "MY_MOD_MARK",                         // уникальная метка: уже внедрено — слой пропускается (идемпотентно)
    slot: 10,                                      // порядок нескольких слоёв одного файла, меньше — раньше
    apply: (source) => source + "\n// MY_MOD_MARK\n// здесь пишется добавляемый код\n",
  });
} else {
  // старый лаунчер без шины: можно вернуться к своему хуку или вообще ничего не внедрять
}
```

Четыре правила (🟥 нарушите любое — другие моды откажут без видимой причины):

| Правило | Почему |
| --- | --- |
| Использовать только `register`, **не** вешать самому `Module.prototype._compile` | Свой хук возвращает «борьбу за точку внедрения», и шина не видит ваши изменения |
| `apply` **только дописывает**; не переписывайте и не удаляйте существующее | Следующие слои должны получить ваш результат и продолжить дописывать |
| `marker` — уникальная строка, которой не пользуются другие | По ней шина понимает, был ли уже внедрён слой, поэтому перезапуск ничего не наслаивает |
| Проверять **префикс до изменения** (или длину), а не sha256 всего файла | Полный хеш в цепочке из нескольких слоёв никогда не совпадёт — это запирает вас самого |

🟩 Как читать результат: в логе `[EveJS-MOD] <файл> внедрено N слоёв (A -> B байт)` — этот слой сработал; `[EveJS-MOD] <id> патч не удался, результат предыдущего слоя сохранён: <причина>` — слой пропущен (**не** влияет на другие моды).
