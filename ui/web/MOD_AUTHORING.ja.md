# EveJS 模組作成チュートリアル（作者の視点）

> **模組を作りたい人**向け：ゼロから模組マーケットでインストールできる模組まで、全 **8 ステップ**。
> 途中で**サーバー側のファイルを書き換える必要はありません** —— 模組はローダー経由で組み込まれます。

**必要なもの**：Windows 10 以上、EveJS サーバー（0.12.8 以降）、EvEJS ランチャー 0.1.20 以上、GitHub アカウント。

---

# 第 1 部：準備（一度きり）

## ステップ 1 ✅ 環境を確認する

1. ランチャーを開く → **環境セルフチェック**：Node.js / 依存関係 / クライアントパスなど 9 項目。赤いものを先に解消します。
2. EveJS サーバーのルート（`server/`、`config/` を含む）を確認します。ランチャー → **設定センター**に現在のパスが出ます。
3. **`mods/` フォルダ**があるか確認します。無ければ 模組 / プラグイン → **mods/ を自動作成**。

🟨 **注意**：模組フォルダは `<EveJS ルート>/mods/<模組 ID>/` に固定です。**別の場所に置かない**でください。日本語（非 ASCII）のフォルダ名にもしないでください。

---

## ステップ 2 ✅ 作者アイデンティティを作成する（「あなたが誰か」の証明）

模組 / プラグイン → 上部の **トークン設定**（作者アイデンティティと GitHub トークンは同じダイアログにあります）：

1. **初回に開くと Ed25519 鍵ペアが自動生成されます**（ボタン操作は不要）
2. **表示名**を変更（人に見せる名前。例：「司令官」）→ **表示名を保存**
3. **鍵を書き出す** をクリック → `.eve-key` ファイルとして**安全な場所**へ保存（USB メモリ / パスワードマネージャー）
4. 別の PC に移すとき：新しい PC で **鍵を読み込む** を押してこの `.eve-key` を選ぶと、アイデンティティが復元されます
5. **鍵フォルダ** ボタンで秘密鍵のあるフォルダ（`_launcher/data/mod-keys/`）を直接開けます

得られるものは 3 つです：

| もの | 説明 | 保管が必要か |
| --- | --- | --- |
| **作者 ID**（`au-...`） | 模組マニフェストに書かれ、「この模組はあなたの作」を表す | 自動的にマニフェストへ書き込まれる |
| **鍵フィンガープリント**（`keyId`、12 文字） | 署名の検証に使う | 自動的にマニフェストへ書き込まれる |
| **`.eve-key` ファイル** | 中身は**秘密鍵** | 🟥 **必ず厳重に保管** |

🟥 **危険**：
- **`.eve-key` はあなたの身元そのもの**です。失う → **二度と更新に署名できなくなります**（既存ユーザーには「署名に失敗しました」と表示されます）。漏れる → 他人があなたとして公開できます。
- `.eve-key` や `_launcher/data/mod-keys/*.key` を GitHub にコミットしたり、他人に渡したり、ZIP に入れたり**絶対にしない**でください。

🟩 **推奨**：PC を移すときは「鍵を読み込む」で `.eve-key` を戻せば、アイデンティティが復元されます。

---

## ステップ 3 ✅ GitHub トークンを作成する（公開と投稿の両方で必要）

ランチャーはあなたの代わりに GitHub を操作します：**公開**時は自分のリポジトリへファイルを書き、Release を作成し ZIP をアップロードします。**収録申請**時は索引リポジトリ `diguo520/EVEjs-mods`（メンテナー名義）をフォークして PR を開きます。**classic トークン** 1 つで両方をまかなえます。

### 3.1 正しいページを開く 🟨

```
GitHub 右上のアイコン → Settings → 左カラムの最下部 Developer settings
  → Personal access tokens → Tokens (classic) → Generate new token (classic)
```

下の画像どおりにクリックします（番号はページ上の赤丸に対応）：

![GitHub classic トークンページ：① Tokens (classic) ② Generate new token (classic) ③ Note ④ Expiration ⑤ repo にチェック](./github-token-classic.png)

| 番号 | どこをクリック / 何を入力 |
| --- | --- |
| ① | 左カラムの **Tokens (classic)** —— 上の Fine-grained tokens ではない |
| ② | **Generate new token** → **Generate new token (classic)** |
| ③ | **Note**：任意。例 `evejs-launcher` |
| ④ | **Expiration**：90 日を推奨（期限切れ時は作り直し） |
| ⑤ | **Select scopes** で **repo** にチェック（`public_repo` はその下位項目で、repo を選べば含まれます） |

🟥 **fine-grained（細粒度）トークンは使わないでください**：その Repository access は「自分が権限を持つリポジトリ」しか選べず、メンテナー名義の索引リポジトリ `EVEjs-mods` を選べません。フォーク作成と PR 作成にはこのリポジトリへの書き込み権限が必要なので、細粒度トークンでの投稿は必ず `403 Resource not accessible by personal access token` で失敗します。

### 3.2 基本情報を入力する

| 項目 | 入力内容 |
| --- | --- |
| Note | 任意。例 `evejs-launcher` |
| Expiration | 90 日または任意（期限切れ後は作り直し） |

### 3.3 scope にチェックする（重要）🟨

| scope | チェック | 役割 |
| --- | --- | --- |
| **public_repo** | 🟩 必須 | 公開リポジトリの読み書き：Release 作成、ZIP アップロード、フォーク作成、PR 作成のすべて |
| **repo** | 🟨 推奨 | public_repo を含む。ランチャーにリポジトリ作成 / プライベートリポジトリ管理もさせたいときにチェック |

### 3.4 生成してコピーする

**Generate token** をクリック → `ghp_...` の文字列をコピー（🟨 **表示は一度だけ**。ページを閉じると見られません）。

### 3.5 ランチャーに入力する

模組 / プラグイン → **トークン設定** → GitHub トークンの欄 → 貼り付け → **保存**（ローカルに暗号化保存。保存後に権限を自動検証）→ 検証が通れば完了。

> 🟦 **なぜ classic なのか？** 索引リポジトリはメンテナー名義で、細粒度トークンでは書き込めません。**索引リポジトリのコラボレーター**に追加された人だけが細粒度トークンを使えます：Repository access で `EVEjs-mods` を選び、権限は **Contents = Read and write** と **Pull requests = Read and write** にします。

🟨 **注意**：トークンの scope を変更したり作り直した後は、新しいトークンを**もう一度貼り付けて保存**してください。

# 第 2 部：模組を作る

## ステップ 4 ✅ 模組を作成する（スケルトン生成）

模組 / プラグイン → **模組を作成** でフォームを入力：

| 項目 | 必須 | 説明 |
| --- | --- | --- |
| テンプレート | ✅ | `Welcome Broadcast (Example)`（ログイン時の歓迎メッセージ付きの例）/ `Blank Skeleton`（空のスケルトン）。🟩 初回は例で一度通すのがおすすめ |
| 模組名 | ✅ | プレイヤーに表示される名前 |
| ID（id / フォルダ名） | 🟩 | 名前から自動生成。`a-z 0-9 - _ .` のみ使用可。作成後は**変更しない** |
| バージョン | ✅ | 既定は `1.0.0`。新バージョンでは**必ず上げる**（ステップ 8） |
| カテゴリ | ✅ | ゲームプレイ / 経済 / AI / グラフィック / ツール（マーケットはこれで絞り込む） |
| タグ | ⭕ | カンマ区切り。例 `チャット, 初心者` |
| 概要 | 🟩 | 一文。マーケットのカードに表示される |
| 詳細説明 / 機能ポイント | ⭕ | 模組の README に書き込まれる |
| 関連模組 ID | ⭕ | どの模組と関連するか。カンマまたは空白区切り |
| ビルドオプション | — | ☑ サーバーを再起動（既定でオン）、☑ 作成後すぐ有効化（既定でオン）、☑ 作成後すぐ署名（既定でオン） |

**作成** を押すと、`mods/` に次が増えます：

```
mods/<あなたの模組 id>/
├─ evejs-launcher.mod.json    ← マニフェスト（身元・バージョン・カテゴリ・依存）
├─ loader.js                  ← あなたが書くロジック
├─ README.md                  ← 「詳細説明」から生成
└─ CHANGELOG.md               ← バージョン変更履歴
```

🟨 「作成後すぐ有効化」の**チェックを外したときだけ**、`loader.js` は `loader.js.disabled` になります（既定でチェック済みなので、既定では読み込める `loader.js`）。後から切り替えるには **インストール済み** のスイッチを操作するだけです —— スイッチは名前を変えているだけです。

🟨 **マニフェストの必須項目**（ランチャーが検証し、欠けると「マニフェスト検証に失敗」と出ます）：

```
schemaVersion: 3                       ← 3 でなければならない
id / displayName / version             ← ID / 名前 / バージョン
kind: "loader"                         ← 現状、実際に有効化できるのは loader のみ
restart: "game_server"                 ← none | client | game_server | launcher
activation.strategy: "loader_rename"   ← これでなければならない
フォルダに loader.js か loader.js.disabled が必要
```

## ステップ 5 ✅ 自分のロジックを書く（`loader.js`）

`mods/<あなたの模組 id>/loader.js` を開くと、スケルトンが既に入っています —— 🟩 **このスケルトン自体が動く最小例**です（プレイヤーがログインして 10 秒後にローカルチャットへ 1 通届く）。そのまま書き換えてください。

🟥 **4 つの厳守事項**（スケルトンにすべて書かれています。1 つでも消すと問題が出ます）：

| 約束 | 理由 |
| --- | --- |
| `setImmediate` + 入口チェック（`process.env.EVEJS_GAMESTORE_OWNER_ROLE === "world"`、または入口が `index.js`） | `NODE_OPTIONS` は npm → サーバーへ層ごとに継承され、ラッパープロセスもあなたのファイルを読み込みます。チェックしないと誤ったプロセスで動きます |
| **サーバーの大きなモジュールを直接 `require` しない**（`chatHub` は約 456MB / 645 モジュールを引き上げる） | `require.cache` に現れてから参照を取る：キャッシュヒットで追加メモリゼロ |
| `timer.unref()` | タイマーがプロセスの終了を妨げないようにする |
| 「一度だけ導入」の判定に `globalThis.__xxx` を使う | loader は複数回読み込まれるため。でないとメッセージ重複やリスナー増殖が起きる |

🟨 **パスの規則（最も踏みやすい罠）**：loader 内の `require("./src/...")` は**あなたの模組フォルダ基準**で解決され、サーバーのルートでは**ありません** —— そのまま書くと `MODULE_NOT_FOUND` になります。正しくは先にサーバーのルートを求めます：

```js
const path = require("path");
const serverRoot = path.resolve(__dirname, "..", "..", "server");
const hubPath = path.join(serverRoot, "src", "services", "chat", "chatHub.js");
// 🟨 ここで直接 require しない —— サーバー自身が読み込むのを待つ。完全な書き方は付録 B を参照
```

🟨 **セッション属性**：チャットセッション上の独自属性は**自動同期されません**。直接読み書きすると「静かに失敗」することがあるため、`chatHub` / `sessionRegistry` が提供するインターフェースを使ってください。

🟩 **サーバーのソースを書き換える**必要がある模組（API 呼び出しだけでは足りないもの）は**付録 G** を参照 —— 自分で `Module.prototype._compile` をフックしないでください。

## ステップ 6 🟩 ローカルテスト

1. 模組 / プラグイン → **インストール済み** → 自分の模組を見つけ、スイッチを**オン**にする（作成時に「すぐ有効化」をチェックしていれば不要）
2. ランチャー → コンソール → **ワンクリック起動**（メインサーバー + マーケットサービスのみ起動）
3. ゲームに入って効果を確認
4. 問題があれば 2 か所のログを見ます：
   - ランチャー → **サーバーログ**（システム / メインサーバー / マーケットサービス / クライアント、INFO/WARN/ERROR で絞り込み可能）
   - サーバーのコンソール出力（ランチャー内で見られます）
5. 🟩 **「本当に読み込まれたか、何ミリ秒かかったか」を確認**：サーバー出力で `[EveJS-MOD]` を検索：
   - `loader 準備完了 <あなたの模組> 3ms` —— loader が読み込まれた。`loader 失敗 ... :: <理由>` なら読み込まれていない
   - `loaders-done total=14 failed=0 ms=1086` —— 全模組の読み込み合計時間
   - `<ファイル> N 層を注入（A -> B バイト）` —— バスのパッチが効いた
   - `<id> パッチ失敗、前の層の結果を保持：<理由>` —— この層は飛ばされた（他の模組には**影響しません**）

   🟨 プロセスごとの明細と各層の結果は `_launcher/logs/mod-load-report.json` にも書かれます。「誰がファイルを書き換えたか」を調べるときはこれを直接見てください。

### 🔧 トラブルシューティング早見表

| 症状 | 最もありそうな原因 |
| --- | --- |
| 一覧に「loader.js がありません」と出る | ファイルが削除された、または別名に変えられた |
| スイッチを入れたのに勝手に切れる | マニフェスト検証の失敗 / 署名が書き換えられた → カードの赤い表示を見る |
| ログに「模組を読み込み」が出ない | 模組が**無効**、または他の模組と衝突して飛ばされた |
| ログに `MODULE_NOT_FOUND` | `require("./src/...")` がサーバーのルート基準と解釈された —— 実際はあなたの模組フォルダ基準（ステップ 5） |
| ゲームで効果がなく、ログにもエラーがない | ロジックが「一度だけ導入」の判定前に return している、または `require` のパスが誤り |
| Node のメモリが急増する | サーバーの大きなモジュールを `require` した（ステップ 5 の罠 2） |

# 第 3 部：マーケットへ公開する

> **公開はワンクリック**：ランチャーが「再署名 → ZIP 作成 → 自分のリポジトリへ push（リポジトリ作成・Release 作成・ZIP アップロード）→ 索引リポジトリへバージョン審査 PR を提出」まで連続で実行し、あなたは進捗バーを見るだけです。
> 索引リポジトリへの PR は**毎バージョン提出**します —— マージされて初めてマーケットが新バージョンに切り替わります。

## ステップ 7 ✅ 公開してマーケットに載せる（ワンクリック）

模組 / プラグイン → **模組を公開**（「作成した模組」カードの「審査に提出 / 再提出」も同じダイアログです）：

1. **模組を選択**：プルダウンには**自分が作成した模組だけ**が出ます（誤投稿を避けるため他人の模組は出ません）
2. **バージョン番号**と**更新内容**を入力（更新内容は索引と PR に書かれます。普通の言葉で）
3. **カテゴリ / タグ**を確認。**ソース / プロジェクト URL** ⭕ 任意（例 `https://github.com/あなた/あなたの模組`）、**GitHub Releases 直リンク** ⭕ 空欄で可（公開時に正しいアドレスが生成されます）
4. 3 つの宣誓にチェック（自作である / 悪意あるコードを含まない / 規約と条件を読んだ）
5. **公開** をクリック

ダイアログ上部の前提条件が揃わないと「公開」は押せません：**表示名**（ステップ 2）、**GitHub トークン**（ステップ 3）、**同じ模組の提出間隔 30 分**、**公開と公開の間隔 60 秒**。足りない項目はその行が黄色くなり、補うための入口が出ます。

### 進捗の 4 段階

| 段階 | やっていること | どこで |
| --- | --- | --- |
| ローカルでパッケージ作成 | 再署名 → ZIP 作成 → SHA256 計算 → マーケット用マニフェスト生成 | **すべてローカル**：通信なし、トークン不要 |
| ソースリポジトリの準備 | リポジトリが無ければ公開リポジトリを作成 | あなたの GitHub |
| Release を公開してパッケージをアップロード | `evejs-mod.json` を書き込み（マーケットが読むもの）→ Release 作成（tag = `v<バージョン>`）→ `<id>-<バージョン>.zip` をアップロード | あなたの GitHub |
| バージョン審査 PR を提出 | 索引リポジトリへ PR：初回は `sources.json`（収録登録）も追加、以降は各バージョンで `mods/<id>.json` のみ更新 | 索引リポジトリ `diguo520/EVEjs-mods` |

生成物と台帳：

| 生成物 | 場所 |
| --- | --- |
| ZIP パッケージ | `_launcher/temp/export-<id>-<version>.zip`（同じものをあなたの Release にもアップ） |
| 提出台帳 | `_launcher/data/my-submissions.json` |

🟨 **コードを変えたら「公開」をもう一度押す**：内容が変われば署名は無効になります。ランチャーが再署名・再パッケージ・再 push を行います。

### 🔧 この段階でよくあるエラー

| エラー | 原因 | 解決方法 |
| --- | --- | --- |
| 🟥 `403 Resource not accessible by personal access token` | トークンが fine-grained、または classic で public_repo 未チェック | classic トークンで **public_repo** をチェック。索引リポジトリはメンテナー名義で細粒度トークンでは届きません。既に索引リポジトリのコラボレーターなら：細粒度トークンで `EVEjs-mods` + Contents / Pull requests = Read and write |
| 🟥 `net::ERR_INVALID_ARGUMENT` | 旧ランチャーの ZIP アップロードのバグ | **0.1.20 以上**へ更新 |
| 🟥 `404` | リポジトリが無い、またはトークンが対象外 | owner/repo の綴りを確認。投稿は classic トークン（public_repo / repo）を使う |
| 🟥 `GitHub トークンが未入力` | トークン未保存 | ステップ 3.5 に戻る |

🟩 **成功後**：ダイアログにリポジトリと Release のアドレスが出ます（開いて ZIP があるか確認できます）。カードは **審査中** になります。

### 審査とマージ

- メンテナーが PR で模組を審査します（マニフェストの項目、カテゴリ、ZIP の場所、バージョン番号など）
- **承認（マージ）**：索引の CI が即座に再構築し、マーケットがあなたのバージョンに更新され、全員のランチャーから検索できます
- **不承認**：メンテナーが PR で理由を返信し、**作成した模組** のカードが赤くなって**収録拒否の理由**が書かれます

🟨 **同じ模組の提出は最短 30 分間隔**：連打すると Release を重複して push し、同じ PR を何度も更新してしまいます。ダイアログに残り時間が出て、それまではボタンが灰色です。

🟦 提出後、ランチャーは**もう一度** PR を確認し、本当に開かれたかを確かめて番号と状態を台帳に記録します：
「作成した模組」カードには `審査中 / マージ済み / PR クローズ` が表示されます（この状態の再確認は最大 30 分に 1 回で、GitHub に頻繁に負荷をかけません）。

# 付録 B：そのまま動く loader スケルトン

これは「模組を作成」が生成するスケルトンの**簡略版**です —— 4 つの厳守事項はすべて入っています。書き換えれば使えます（コメント付きの完全版は `mods/<あなたの模組 id>/loader.js` を直接見てください）：

```js
"use strict";
const path = require("path");

const TAG = "[わたしの模組]";
const MOD_ID = "my-mod";
const POLL_MS = 3000;
const GRACE_MS = 10000;                      // ログイン後これだけ待つ：セッションが先に準備される必要がある
const MESSAGE = "おかえりなさい、パイロット！";

// サーバーソースを変えるならこのブロックを開く（新方式：バスへ申告し、追記のみ）：
//   target —— EveJS ルートからの相対、スラッシュ区切り
//   marker —— 一意なマーク。すでに存在すればバスがその層を飛ばす（冪等）
//   slot   —— 同じファイルに複数層あるときの順序。小さいほど前（10 の倍数を推奨）
//   append —— 追記するコードのみ。全体を書き直さない
const SOURCE_PATCH = null;
// const SOURCE_PATCH = {
//   target: "server/src/network/tcp/handshake.js",
//   marker: "// my-mod:patch",
//   slot: 40,
//   append: "// my-mod:patch\nconsole.log('[my-mod] patched');",
// };

console.log(TAG + " preload を実行 · pid=" + process.pid);

/** 本当のサーバープロセスでのみ続行する（npm / ラッパープロセスを除外） */
function isRealServerProcess() {
  if (process.env.EVEJS_GAMESTORE_OWNER_ROLE === "world") return true;
  const entry = (require.main && require.main.filename) || process.argv[1] || "";
  return /(^|[\\/])index\.js$/i.test(entry);
}

/** ソースパッチを注入バスへ登録する（🟥 同期実行が必須。理由は下） */
function registerSourcePatch() {
  if (!SOURCE_PATCH || !SOURCE_PATCH.target) return;
  const bus = globalThis.__evejsMods;
  if (!bus || !(Number(bus.api) >= 1)) {
    console.log(TAG + " 旧ランチャーには注入バスが無いため、ソースパッチをスキップ");
    return;
  }
  bus.register({
    id: MOD_ID,
    target: SOURCE_PATCH.target,
    marker: SOURCE_PATCH.marker,
    slot: SOURCE_PATCH.slot,
    apply: (source) => source + "\n" + SOURCE_PATCH.append + "\n",
  });
}
// 🟥 同期的に登録する：サーバーは起動時にターゲットを require するので、
//    setImmediate に入れてから登録すると遅い（その時点でコンパイル済みで、パッチは効かない）
registerSourcePatch();

setImmediate(() => {
  if (!isRealServerProcess()) return;
  if (globalThis.__myModStarted) return;      // 🟨 複数回読み込まれる：一度だけ導入する
  globalThis.__myModStarted = true;
  start();
});

function start() {
  // 🟥 require("./src/...") は**あなたの模組フォルダ**基準で、サーバーのルートではない —— 先にルートを求める
  const serverRoot = path.resolve(__dirname, "..", "..", "server");
  const hubPath = path.join(serverRoot, "src", "services", "chat", "chatHub.js");
  const registryPath = path.join(serverRoot, "src", "services", "chat", "sessionRegistry.js");

  // 🟨 サーバー自身がこの 2 つを require.cache に入れるまで待ってから参照を取る：
  //    キャッシュヒット、追加メモリゼロ、456MB のモジュールグラフを早く引き上げない
  const timer = setInterval(() => {
    if (!require.cache[require.resolve(hubPath)]) return;
    if (!require.cache[require.resolve(registryPath)]) return;
    clearInterval(timer);
    run(require(require.resolve(hubPath)), require(require.resolve(registryPath)));
  }, 500);
  timer.unref();
}

function run(chatHub, sessionRegistry) {
  const seen = new Set();
  const firstSeenAt = new Map();

  const timer = setInterval(() => {
    let sessions;
    try {
      sessions = sessionRegistry.getSessions() || [];
    } catch {
      return;
    }

    const now = Date.now();
    const online = new Set();

    for (const session of sessions) {
      const characterID = sessionRegistry.resolveSessionCharacterID(session);
      if (!characterID) continue;              // まだ本当にゲーム内ではない。次の周回を待つ
      online.add(characterID);
      if (!firstSeenAt.has(characterID)) firstSeenAt.set(characterID, now);
      if (seen.has(characterID)) continue;
      if (now - firstSeenAt.get(characterID) < GRACE_MS) continue;

      try {
        // セッションによっては小文字 charid しか持たないので補う（「静かに送信されない」の回避）
        if (!Number(session.characterID || 0)) session.characterID = characterID;
        chatHub.sendSystemMessage(session, MESSAGE);
        seen.add(characterID);
        console.log(TAG + " キャラクター " + characterID + " にメッセージを送信しました");
      } catch (error) {
        console.log(TAG + " キャラクター " + characterID + " はまだ準備できていません。後で再試行：" + error.message);
      }
    }

    // オフラインになったキャラクターを消す。次のログインで再度発火する
    for (const id of Array.from(seen)) if (!online.has(id)) seen.delete(id);
    for (const id of Array.from(firstSeenAt.keys())) if (!online.has(id)) firstSeenAt.delete(id);
  }, POLL_MS);
  timer.unref();
}
```

🟨 上で使っているサーバーインターフェースは**実測で使えることを確認済み**です：

| インターフェース | 用途 |
| --- | --- |
| `sessionRegistry.getSessions()` | オンラインセッションの配列（🟥 `list()` **ではない**。そのメソッドは存在しません） |
| `sessionRegistry.resolveSessionCharacterID(session)` | キャラクター ID を取得（ゲームに入る前は 0） |
| `chatHub.sendSystemMessage(session, "メッセージ")` | そのキャラクターのローカルチャンネルへシステムメッセージを送る |

EveJS のバージョンによってインターフェースは変わり得ます。あなたのバージョンの実際のエクスポートを基準にしてください。

# 付録 C：衝突と読み込み順

| 種類 | 発生の仕方 | 結果 |
| --- | --- | --- |
| 宣言された衝突 | マニフェストの `conflicts` が互いを書いている | 2 つの模組は同時に有効化されない |
| `id` の重複 | 2 つのフォルダのマニフェスト `id` が同じ | 片方だけが読み込まれる |
| サーバーモジュールの共用 | 複数の loader が同じサーバーモジュールを参照 | 互いに影響し合う可能性（ランチャーが警告） |
| 依存の欠落 | `requires` の模組が未インストール | その模組は読み込まれない |

🟦 読み込み順：**インストール済み** でカードを**ドラッグ**して並べ替えられます。カード左上の「⤓ 最後に移動」も使えます。一覧は「有効が先・無効が後」に分かれ、各段の中はあなたが決めた順です —— 無効にしても並べ直す必要はなく、戻すと元の位置に復帰します。
🟨 マニフェストの `loadAfter` / `loadBefore` は**優先度が高く**、ドラッグした順に割り込んで微調整します。位置が動いた模組は「読み込み順」パネルで「マニフェストの制約で移動」と表示されます。
🟦 「読み込み順」パネルには**実際に効いている**順序と、**今回読み込まれない**模組（マニフェスト不正 / 依存不足 / 競合 / loader.js なし）、**効かなかった順序宣言**（対象が未インストールまたは無効、保存済み順序のフォルダが消えた）が並びます。変更は**サーバー再起動後**に反映されます。

## 🟥 複数の模組が同じサーバーファイルを書き換える（新ランチャーには解決策がある）

模組が**自前で `Module.prototype._compile` をフック**してサーバーソースを変えていると、2 つの模組が同じファイルを触った時点で問題が起きます：

- どちらが先に元のファイルを見るかは読み込み順に完全に依存する；
- 片方が「ファイル全体の sha256」で検証していると、もう片方がすでに追記しているため**検証に失敗**する；
- 実際に観測された例：`自動採掘` と `自動ロック・自動集火` がどちらも `server/src/network/tcp/handshake.js` の末尾へコードを追記し、先に注入した方が書き込んだ後、後に注入した方はハッシュが合わず**静かに諦めた**（エラーも出ず、効果も出ない）。

🟩 新ランチャーはそのために**注入バス**を用意しました：模組は個別にフックせず、`__evejsMods.register` で「どのファイルに何を加えるか」を宣言し、バスが `(slot, 登録順)` で 1 本のチェーンにします —— 各層は**前の層が変えた後**の内容を見ます。使い方は**付録 G**。

# 付録 D：ZIP の構造とインポート規則

### ZIP の構造（どちらも対応、方式 2 を推奨）

```text
方式 1：ルート直下にマニフェスト        方式 2：1 階層のフォルダで包む（推奨）
my-mod.zip                          my-mod.zip
├── evejs-launcher.mod.json          └── my-mod/
├── loader.js.disabled                   ├── evejs-launcher.mod.json
└── README.md                            ├── loader.js.disabled
                                          └── README.md
```

ランチャーはパッケージのルートを自動で特定します。ZIP に**複数の**模組パッケージが入っていると拒否されます（1 回につき 1 つだけ）。

### 他人があなたの ZIP をインポートするときの規則

| 規則 | 説明 |
| --- | --- |
| インストール先 | `<EveJS ルート>/mods/<マニフェスト id>`（id の不正な文字は `-` に置換） |
| 初期状態 | **強制的に無効**（`loader.js` は `loader.js.disabled` に戻される）。ユーザーが手動で有効化 |
| 同名の衝突 | `mods/` に同名フォルダがある → インポートを拒否して通知 |
| マニフェスト欠落 | ZIP に `evejs-launcher.mod.json` が無い → 拒否 |

### 🟨 サイズ

模組ページは**各模組の使用容量を再帰的に集計**します。動作に必要なファイルだけをパッケージしてください —— 🟥 ソースリポジトリ、`node_modules`、スクリーンショット、`.git` を ZIP に入れないでください。

# 付録 E：loader はどのように注入されるか

🟩 **現在（注入バス経由）**：ランチャーは `NODE_OPTIONS` に `--require "<ランチャー同梱の mod-host.js>"` を**1 つだけ**入れ、あなたの `loader.js` はバスが `_launcher/mods/mod-plan.json` の順に `require` します。そのため模組フォルダ名に非 ASCII や空白があっても問題ありません。ランチャーのログの `[EveJS-MOD] loaders-done total=N failed=0 ms=X` が「全模組の読み込みに何ミリ秒かかったか」です。

🟨 **以下は「loader ごとに 1 つの `--require`」という旧方式**（現在はバスのプラン書き込みが失敗したときの保険としてのみ使用）：ランチャーは Node の `NODE_OPTIONS=--require ...` であなたの `loader.js` をサーバープロセスへ注入します。したがって：

- 🟥 **バックスラッシュはエスケープとして飲み込まれる** → `C:\mods\x\loader.js` は `C:modsxloader.js` になる
- 🟨 `NODE_OPTIONS` は空白で分割されるため、**空白を含むパスは引用符で囲む必要がある**

正しい書き方は「パスをスラッシュに変換 + 二重引用符で囲む」 —— ランチャー内部もこう組み立てています（実測済み）：

```js
const requireArgs = paths.map((p) => '--require "' + p.replace(/\\/g, "/") + '"').join(" ");
```

🟦 あなたが自分でこれを組み立てる**必要はありません** —— 「模組フォルダに非 ASCII や空白を入れない」とだけ覚えておけば、トラブル時に突き合わせられます。

# 付録 G：サーバーソースを変える —— 注入バス `__evejsMods.register`

🟨 **サーバーソースを変える必要がある**模組だけがこの部分を必要とします。「ログイン挨拶」のようにサーバー API を呼ぶだけの模組は付録 B で十分です。

バスはランチャーが注入します。模組側はファイル末尾で宣言するだけです：

```js
const bus = globalThis.__evejsMods;
if (bus && bus.api >= 1) {
  bus.register({
    id: "あなたの模組 id",                          // マニフェストの id と同じ。レポートで使われる
    target: "server/src/network/tcp/handshake.js",  // EveJS ルートからの相対、スラッシュ区切り
    marker: "MY_MOD_MARK",                         // 一意なマーク：すでに注入済みなら自動でスキップ（冪等）
    slot: 10,                                      // 同じファイルに複数層あるときの順序。小さいほど前
    apply: (source) => source + "\n// MY_MOD_MARK\n// ここに追記したいコードを書く\n",
  });
} else {
  // 旧ランチャーにはバスがない：自前フックへ戻すか、何も注入しない
}
```

4 つの約束（🟥 どれか 1 つでも破ると他の模組が原因不明で動かなくなります）：

| 約束 | 理由 |
| --- | --- |
| `register` だけを使い、**自分で** `Module.prototype._compile` をフックしない | 自前フックは「注入点の取り合い」に戻り、バスからもあなたの変更が見えなくなる |
| `apply` は**追記のみ**。既存内容を書き直したり削除したりしない | 後続の層があなたの結果を受け取って追記を続ける必要がある |
| `marker` は他人が使わない一意な文字列にする | バスはこれで注入済みかを判定し、再起動で重ねて注入しない |
| 検証するなら**変更前のプレフィックス**（または長さ）を見る。ファイル全体の sha256 は使わない | 多層チェーンでは全体ハッシュは必ず合わず、自分を詰ませる |

🟩 結果の見方：ログの `[EveJS-MOD] <ファイル> N 層を注入（A -> B バイト）` はこの層が効いたという意味、`[EveJS-MOD] <id> パッチ失敗、前の層の結果を保持：<理由>` はこの層が飛ばされた（他の模組には**影響しません**）という意味です。
