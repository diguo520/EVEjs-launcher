## 2. 一条红线（先记住，别踩）

现役 Electron 0.1.28 的自动更新器读的是：

```
https://github.com/diguo520/EVEjs-launcher/releases/latest/download/update-manifest.json
```

它**只核 sha256、不认 zip**，会把清单里指向的文件当成 exe 直接替换主程序。所以：

- ❌ **绝不能**把 Tauri 的 `update-manifest.json` + 便携 zip 发到 `releases/latest`（等于静默毁掉现役用户的启动器）。
- ✅ 源码替换（本文主题）与更新通道切换**分开做**；新通道走 `releases/download/stable/...`（详见 `docs/S7-发布与回滚-实施记录.md` §2）。
- ✅ 不删 tag、不动 v0.1.28 的 release 资产 —— 这样旧用户的自动更新永远停在 0.1.28 停机页，不会拿到错包。

## 3. 推荐执行顺序

> 若决定**旧 Electron 文件一份不留**（只保留 Releases 与 Wiki），直接跳 §9 路线 C。

```
第 1 步  推送 tauri2 分支（路线 B 的默认动作）  → 触发 CI，校准首次流水线
第 2 步  CI 绿了再决定 main 怎么切              → 路线 A（原地替换，已演练）
第 3 步  发布侧收尾（stable tag + 签名公钥 + 停机页）
```

先推分支的好处：**不改 `main`、不动 release、随时可弃**，而且能在真实 runner 上把 CI 跑通一次。

## 4. 路线 A：原地替换 `main`（不丢历史、不需要强推）

### 4.1 做法

不要在现有工作区里切分支（本地新文件全是 untracked，会和远端同名文件撞车）。**用一个临时 clone 做装配**，
装配好一次性推上去，现有工作区完全不受影响。

```powershell
$tmp = "$env:TEMP\evejs-swap"
Remove-Item -Recurse -Force $tmp -ErrorAction SilentlyContinue
git clone --branch main https://github.com/diguo520/EVEjs-launcher $tmp
cd $tmp

# ① 删除旧框架独有内容（这些路径在新框架里不存在）
git rm -r --quiet -- `
  src updater build assets/eve-console docs/screenshots `
  electron-builder.yml tsconfig.json tsconfig.main.json vite.config.ts package-lock.json `
  assets/paypal.png assets/shoukuanma.png assets/wechat.png `
  .github/workflows/release.yml .github/workflows/backfill-release-notes.yml `
  scripts/account-cli.js scripts/check-renderer.js scripts/database-cli.js `
  scripts/delete-account.py scripts/release-notes-body.mjs

# ② 把新框架源码覆盖进来（排除产物与本地临时目录）
robocopy "E:\AI projects\ChatGPT\evejs-launcher" $tmp /E /XD `
  .git .parity-out artifacts .audit node_modules target dist app-dist
# 注：不要加 /XF .gitignore —— 仓库里还有 assets\.gitignore（原型工程自己的），会被一起排掉

# ③ 用 §10 的合并版 .gitignore 覆盖 $tmp\.gitignore（旧仓的 _launcher/ 等条目在新框架里同样有用）

git add -A
git status --short          # 提交前最后肉眼过一遍
git commit -m "feat: Tauri 2 新框架启动器源码（替换 Electron 版）/ migrate launcher to Tauri 2"
git push origin main        # 普通推送即可，无需 --force
```

保留在 `main` 里的旧内容（**刻意不删**）：

| 路径 | 为什么留 |
| --- | --- |
| `release-notes/v0.1.*.json`（24 份） | 版本历史归档，旧用户回看更新日志要用 |
| `AGENTS.md` | 开发/发布约定（版本节奏 = 8 个改动一版），对新框架同样适用 |

| `README.md` | **必须重写**（见 §5 第 1 条），不能留着讲 Electron |
| tag `v0.1.6` … `v0.1.28` + Releases | 旧用户自动更新的唯一安全落点，永久保留 |

## 5. 推送前必须补的 6 件事

1. **README 重写**：本地仓库根目录**没有 README.md**，装配后会沿用旧仓那份「Electron 版」说明。
   必须改成新框架版（Tauri 2 / 体积 / 启动速度 / 安装包与便携版下载 / 界面截图 / 从旧版迁移说明），
   中英双语各一段，`## 中文` 锚点保留（你给的那个链接就指向它）。
2. **LICENSE 决策**：旧仓没有协议 = 默认「保留所有权利」，和「开源」矛盾。三选一：
   MIT（最宽松，社区友好）／ Apache-2.0（含专利授权，企业友好）／ GPL-3.0（衍生必须开源）。
   定了之后加 `LICENSE` 并在 README 里标注。
3. **`release-notes/` 续写**：旧仓 `pending.json` 写的是 `nextVersion: 0.1.29`，新框架本地版本是 `0.2.0`。
   建议新版本直接打 `v0.2.0`，并加 `release-notes/v0.2.0.json`（schema 沿用旧仓 AGENTS.md 的
   `{version, changelog:{zh[],en[]}}`，`type` 仅 `new|fix|opt`），同时把 `pending.json` 重置为
   `nextVersion: 0.2.1`。这样旧仓的更新日志读取逻辑不用改。
4. **`docs/screenshots/*.png`（5 张旧 UI 截图，≈2.9 MB）**：已在 §4.1 里删除，需要换成本仓库
   `.parity-out/shots/` 里的新 UI 截图（真机核验过的那批），并同步 README 引用路径。
5. **Go 工具链**：`vendor/updater/bin/evejs-updater.exe` 被 `.gitignore` 的 `*.exe` 规则排除，**不入库**；
   `scripts/build.ps1` 在缺失时会现场 `go build`（源码 `vendor/updater/main.go` 已入库，与 Electron 时代是同一份）。
   所以新克隆要能构建，README 必须写明「需要 Go 工具链」，否则就把预编译 updater 作为 Release 附件提供。
6. **`assets/` 原型是否入库**：本仓库 `assets/`（132 文件）是你重做界面用的 shadcn 原型工程（自带
   `package.json`/`pnpm-lock.yaml`），和 `ui/` 是两套前端。已演练为**一并入库**（当设计原型归档）。
   若不想公开原型，从 `TOP` 列表里去掉 `assets` 即可，`ui/` 才是真正编译进 exe 的那套。

## 9. 路线 C（本次选定）：孤儿 `main` —— 只留 Releases 与 Wiki，其余全部替换

### 9.1 可行性判定（实测）

| 资产 | 是否受影响 | 依据 |
| --- | --- | --- |
| Releases（21 个，v0.1.6 … v0.1.28） | **不受影响**，但**依赖 tag** | Release 锚在 tag 上，资产下载地址是 `/releases/download/<tag>/<file>` |
| Wiki | **完全不受影响** | Wiki 是独立仓库 `EVEjs-launcher.wiki.git`（实测 HEAD `28078adb`，**有内容**），跟主仓无关 |
| 模组市场清单 | **不受影响** | 走 `https://diguo520.github.io/EVEjs-mods/mod-index.json` 与 jsDelivr `diguo520/EVEjs-mods@main`（**另一个仓库**，实测 200 / 5,442 B） |
| Issues / Stars / Forks / 仓库设置 / Actions 密钥 | 不受影响 | 与 main 无关（实测 0 open issue、0 fork、1 star） |
| GitHub Pages | 本来就没有（`has_pages=false`） | — |
| 新外壳自身 | 只依赖 `releases/latest/download/update-manifest.json`（`src-tauri/src/updater.rs:27`） | 与 main 内容无关 |

结论：**能做到**。两条硬约束见下。

### 9.2 硬约束一：21 个 tag 必须保留

- 删 tag → Release 变 `untagged`，`releases/download/<tag>/<file>` 全 404，`releases/latest/download/update-manifest.json` 一并失效 → 老用户更新检查直接报错。
- 留 tag → 旧提交仍可达（`git clone --branch v0.1.28` 还能取到 Electron 源码），但**默认视图与 `main` 历史里一份不留**。仓库体积仍约 9.5 MB，这是「Releases 继续可用」的代价。
- 想把对象库也清空，只能把 tag 重指到新提交 —— 等于伪造发布历史，**不推荐**。

### 9.3 硬约束二：别让新 Release 顶掉 `releases/latest`

发布 `v0.2.0` 后 GitHub 会把 `latest` 指向它 → 老 Electron 客户端读到的就是 Tauri 的新 manifest → zip 被当 exe 替换 → **用户启动器报废**。三选一：

- ✅ 发布后在 v0.1.28 的 Release 页面点 **Set as the latest release**，把 `latest` 钉死；
- ✅ 或给新 Release 勾 **Pre-release**（`latest` 会跳过它，100% 确定有效）；
- ✅ 终局：按 `docs/S7-发布与回滚-实施记录.md` §2.3 给旧通道发 **0.1.29 停机页包**（只做公告 + 引导下载新启动器）。

### 11.7 方案 B：单文件 exe（缓存仍落 `_launcher`）

用户选定：**不打包 zip、不做安装器**，双击一个 exe 就能跑；启动器缓存（`data/` `cache/` `cli/`
`updater/` `mods/` `temp/`）仍然落在 exe 同级的 `_launcher/`。

必须落盘才能执行的东西有两类：Node CLI（`node <脚本>` 子进程）与自更新器（直接 CreateProcess 的 .exe）。
做法：

| 文件 | 改动 |
| --- | --- |
| `src-tauri/build.rs`（新增） | 把 `vendor/updater/bin/evejs-updater.exe` 拷进 `OUT_DIR` 供 `include_bytes!`；文件不在就写**空占位**，干净 clone / CI 上照样编过（只是不嵌）；带 `rerun-if-changed` |
| `src-tauri/src/seed.rs`（新增） | `ensure_bundled_sidecars(exe_dir)` 启动时把内嵌的 `account-cli.js` / `database-cli.js` / 更新器释放到 `<exe 同级>/_launcher/cli|updater/`。**内容不一致才写**（先比长度再比字节）→ 幂等、不刷时间戳、被改坏能自愈。**不写 `runtime.root`**（`EVEJS_USER_DATA_DIR` 会把它指到别处，而查找函数认 exe 同级） |
| `src-tauri/src/lib.rs` | 在 `legacy::adopt` 之后调用；释放失败**不拦启动**，相关功能自己报「找不到脚本」 |
| `scripts/build.ps1` | 新增步骤 `6b`（先 `go build` 更新器）并提到 cargo build **之前**，否则 `include_bytes!` 拿到的是空占位 |

尺寸实测：`EvEJSLauncher.exe` = **9.24 MB**（原 7.33 MB + 内嵌资源），过体积门禁（≤ 12 MB）；
对照现役便携版 72.95 MB = **缩小约 7.9 倍**。
