# EvEJS 启动器 · 换壳（框架迁移）方案

> 日期：2026-09-25
> 目标：在功能不缩水的前提下，把现有 Electron 启动器换成体积小、启动快、内存占用低的方案。
> 现役代码：`E:\Games\EveJS-v0.12.8\launcher\launcher`（v0.1.28）
> 新工程目录：`E:\AI projects\ChatGPT\evejs-launcher`

### 1.1 关键发现：渲染层是纯 HTML/CSS/JS，不是 React

生产入口是 `dist/renderer/eve-launcher.html`（由 `public/` 原样拷贝），`src/main/index.ts` 里窗口加载的就是它：

```ts
void mainWindow.loadFile(path.join(__dirname, "../../renderer/eve-launcher.html"));
```

`src/renderer/*.tsx`、`react`、`react-dom`、`@xterm/xterm`、`@xterm/addon-fit` 在当前产物中**并未被使用**
（`vite build` 产出的 `index.html` 无人加载）；终端也不是 xterm.js，而是 `launcher-bridge.js` 里自绘的
DOM 日志控制台（`ansiPattern` 去色 + INFO/WARN/ERR 分级）。

> **这条结论决定了整个迁移策略**：换到任何 WebView2 壳，UI 与样式可以 **0 改动复用**，
> 迁移工作全部集中在主进程（Node → Rust），规模可控。

### 1.2 “启动慢”的真实成因（换壳只能解决第 1 条）

| # | 成因 | 量级 | 换壳能否解决 |
| --- | --- | --- | --- |
| 1 | Electron/Chromium 多进程冷启动 + 主进程 7,986 行 TS 同步初始化 | 1.2–2.5 s | ✅ 换壳可解 |
| 2 | 账号/数据库操作**每次 spawn 一个 node 进程**并加载 `server/node_modules/better-sqlite3`（`execFile("node",[cli])`，20+ 通道） | 0.3–1.0 s / 次 | ❌ 必须改直连 |
| 3 | 指标采集走 PowerShell `Get-CimInstance Win32_PerfFormattedData_GPUPerformanceCounters_*` | 1–3 s / 次（有缓存） | ❌ 必须改 Win32/PDH |
| 4 | 打包 ZIP 走 `powershell.exe` + .NET `ZipFile` | 0.5–2 s / 次 | ❌ 必须改原生 zip |
| 5 | 首屏 `fetch` 解析 4.9 MB JSON + 5.3 MB 手册 | 200–800 ms | ⚠️ 改按需/异步即可 |

**结论：方案必须同时做「换壳」+「打掉 CLI 进程桥」**，只换壳只能拿到一半收益。

## 2. 方案选型

### 2.1 对比

| 指标 | 现状 Electron 33 | **A. Tauri v2（Rust + WebView2）** | B. Wails v3（Go + WebView2） | C. 原生 Rust GUI（egui/Slint） |
| --- | --- | --- | --- | --- |
| 便携 exe 体积 | 73 MB | **6–12 MB**（资源内嵌后 15–25 MB） | 10–18 MB（+资源） | **5–10 MB**（资源需外置） |
| 冷启动到可见窗口 | 1.2–2.5 s | **0.25–0.7 s**（会话首次略高） | 0.3–0.8 s | **0.08–0.25 s** |
| 空闲内存（壳本身） | 180–350 MB（预估） | **80–140 MB**（WebView2 多进程，有下限） | 80–140 MB | **35–70 MB** |
| UI 迁移量 | — | **≈0**（现有 HTML/CSS/JS 直接复用） | ≈0 | **100% 重写**（4,468 行 HTML + 2,333 行 JS 全转 Rust 控件） |
| 后端迁移量 | — | 100%（7,986 行 TS → Rust） | 100%（→ Go） | 100%（→ Rust） |
| 大文件手册 / JSON | 现成 | 直接复用 | 直接复用 | 需转换或另挂 WebView（体积优势反被吃掉） |
| 无边框自绘标题栏 | 现成 | 支持（`decorations:false` + `startDragging`） | 支持 | 支持 |
| 主要风险 | 体积 / 内存无解 | WebView2 运行时依赖、Rust 维护成本 | Wails v3 迭代期 API 变动 | 工期 ×2.5、EVE 视觉难保真 |

### 2.2 推荐：方案 A（Tauri v2）

理由按优先级：

1. **UI 零改动**：`eve-launcher.html` + `launcher-bridge.js` + `eve-theme.css` 原样搬过去，
   只把 `window.api` 的实现从 preload 换成 Tauri `invoke` 包装（**契约不变：83 个方法同名同签名**）。
   这一条把最大风险直接抹掉 —— 不用重画 EVE Neocom 风格界面。
2. **三个指标同时达标**：体积 ↓85%、冷启动 ↓75%、内存 ↓60%。
3. **顺手打掉慢点 2/3/4**：Rust 侧用 `rusqlite`（自带 SQLite，不再依赖 `server/node_modules/better-sqlite3`，
   也不再 spawn node）、`windows` crate 直读性能计数器、`zip` crate 原生打包。
4. **更新器 0 改动**：现有 Go `evejs-updater.exe` 是独立进程替换 exe，与外壳框架无关，直接沿用。

**何时选 B**：团队更熟 Go、能接受 Wails v3 的 API 变动；收益与 A 基本等同。

**何时选 C**：**内存 < 80 MB 是硬指标**时才值得。代价：UI 全部重写、5.3 MB 手册要另做方案、
工期约 ×2.5。建议先做 A，实测后仍不达标再评估 C。

### 3.1 渲染层只需要改一处

现有 `launcher-bridge.js` 第一行就是 `const api = window.api;`，因此只要在页面最前面注入一份
同签名的 `window.api`（内部转 `invoke`）即可：

```js
// ui/api.ts（新增，唯一新增的前端文件）
const call = (cmd) => (...args) => invoke(cmd, { args });
window.api = {
  appInfo: call("app_info"),
  serviceStart: call("service_start"),
  // ... 83 个方法，与 src/preload/index.ts 逐条对齐
};
```

事件方向（PTY 输出、服务状态变化、初始化进度）用 Tauri `Channel` / `emit` 替代
`ipcRenderer.on`，`launcher-bridge.js` 中对应的 `api.onTerminalData(...)` 等回调改为订阅同名事件。

### 3.2 必须逐位对齐的三处语义

| 语义 | 现有实现 | 迁移要求 |
| --- | --- | --- |
| 密码哈希 | `SHA1(pw_utf16le ‖ user_lower_utf16le)` 迭代 1000 次（machobase `PasswordHash`） | Rust `sha1` crate 按位复刻，用现有账号跑回归 |
| 模组验签 | Ed25519 + 内置索引公钥信任链（`modSigner.ts`） | 固定测试向量逐位比对签名结果 |
| 令牌加密 | Electron `safeStorage` | DPAPI（`windows` crate / `keyring`）；注意旧数据兼容或一次性重置提示 |

`eve-launcher.html`（新工程直接引用旧路径），保证界面不漂移；后端按阶段「搬一条、验一条、删一条」，
结束时旧版自然退役。

## 6. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| **WebView2 运行时缺失**（Win10 1809 精简版 / Server） | 启动器打不开 | 启动前查注册表 `HKLM\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-...}`；缺失时引导运行 1.5 MB Evergreen bootstrapper。**不要**用 Fixed Version（+80 MB，等于白换） |
| Rust 技术栈维护成本 | 迭代变慢 | 若团队不愿承担，改走方案 B（Go/Wails），迁移工作量同量级 |
| 验签 / 哈希语义漂移 | 已签模组失效、账号登不上 | P2、P3 各自建立固定测试向量并在 CI 回归 |
| 无边框窗口细节 | 拖拽 / 最大化 / 多屏 DPI 异常 | P0 一次性做完并截图对照（现役为 `frame:false`） |
| 5.3 MB 手册 + 4.9 MB JSON | 首屏卡顿 | 走自定义资源协议按需加载；手册改为点击后异步加载 |
| 迁移期双轨维护 | 需求要改两遍 | 共用同一份 HTML；只允许“旧壳加功能 → 同步搬进新壳”单向流动 |
| 冒烟测试不可直接复用 | 失去回归网 | 保留 `check-renderer.js` 语法预检；冒烟按通道清单重写为 Rust 侧集成测试 |

## 7. 兜底方案 D（1 周见效，但体积 / 内存不达标）

只做 1.2 节的第 2/3/4/5 条（数据库与账号常驻连接替代 node spawn、指标改 Win32、ZIP 改原生库、
大资源异步化），预期：

- 交互延迟 ↓70%（0.3–1 s → 50–150 ms）
- 启动时间 ↓20–30%（1.8 s → 1.2–1.4 s）
- 体积、内存**几乎不变**（73 MB / 200 MB+）

适合作为过渡，解决不了体积与内存诉求。
