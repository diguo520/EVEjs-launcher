## 2. 关键决策

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| **S5-D01** | **跨实现比对不靠上游改源码**：把现役 `dist/` + `scripts/` 复制进 `.parity-out/electron-harness/`，`node_modules` 用 junction，塞入自己的入口 `parity-main.js` 劫持 `ipcMain` 后 `require` 现役的 `registerIpc()` | 原计划要现役版加 3 处 hook，而现役版是**只读**的；这个包装方案一个字节都不改现役源码，却拿到同样的回包原文。试过并被本机策略拦死的两条路（`NODE_OPTIONS=--require`、`--remote-debugging-port`）已放弃，`tests/parity/hooks/probe.js` 删除 |
| **S5-D02** | **归一化口径抽到 `normalize.mjs`**（`compareChannel`/`isEmptyPayload`），`diff.mjs` 与 `diff-cross.mjs` 共用 | 两套 diff 各写一套规则 = 迟早漂移；现在「整体比 / 只比结构」的选择只有一处 |
| **S5-D03** | **跨实现差异走「显式豁免表 + 命中统计」**，而不是把差异塞进 volatile 白名单 | volatile 白名单是「全局降噪」，拿来掩盖实现差异会把 Tauri 自比基线一起削弱；豁免表只豁免**具体键**且必须写明理由，还会打印**未被触发**的条目提醒复核 |
| **S5-D04** | **冻结 Electron 基线**（`electron-baseline.json`），跨实现比对前先自查参考实现有没有漂移 | 参考实现升级（现役版更新）会让跨实现比对悄悄换成「拿新版比旧版」，漂移必须直接红 |
| **S5-D05** | 现役侧 `--parity-dump` **改名**为 `EVEJS_SELF_TEST_DUMP=1` 环境变量 | 保持 A4 的静态断言「生产只注册 `launcher_invoke`、自检命令仅 `--self-test` 注册」原样成立（D 决策沿用 S3-D*，L9 因此算达成等价物） |
| **S5-D06** | 修 `ABS_PATH` 归一化：按**反斜杠分段**匹配 | 旧正则 `[A-Za-z]:[\\/][^\s"']*` 有两个真缺陷：① 路径里的空格（本机仓库目录名就带空格）会把路径截成两半，基线绑死本机目录结构；② 会把 `http://127.0.0.1:26002/` 吃成 `htt<abs-path>` |
| **S5-D07** | `metrics:get` 的虚拟内存改用 Win32 `GlobalMemoryStatusEx`（提交限制），不再用 `sysinfo` 的 swap | 现役版取的是 CIM `TotalVirtualMemorySize/FreeVirtualMemory`（= 提交限制），`sysinfo::swap` 是**完全不同的量**；实测新值 43778 MB 与 `systeminfo` 完全一致 |
| **S5-D08** | `env:check` 的检查项按现役 8 项重写，并抽出 `ENV_CHECK_KEYS` 常量；`check_item` 缺省键**不写 null** | 见 §5.1（这是本轮抓到的最严重缺陷）。现役版是 JS，`undefined` 序列化后键会消失，写 `null` 会让两边键集合不同 |
| **S5-D09** | 新增**跨语言一致性单测**：`env.rs` 的 key 顺序 ↔ 渲染层 `critical` 白名单 / `envKeyMap` ↔ `init::KEYS` | §5.1 那个缺陷是「Rust 与 JS 各写一份、没人对账」造成的，纯 Rust 单测抓不到；现在这个断言在 `cargo test` 里，改任何一边都会红 |
| **S5-D10** | `accounts:checkRunning` 改按**结构**比对；`windowBounds` 归 volatile | 端口列表来自 netstat（随服务启停变化）、`windowBounds` 是用户拖出来的窗口状态，两者都不可能构成「实现差异」，留着比只会制造红灯 |
| **S5-D11** | `parity:cross` 焊进 `build.ps1`：debug 构建跳过（基线是 release 口径）、没有现役 Electron 的机器**明确打印跳过** | CI runner 上没有现役版；「静默跳过」会让门禁变成摆设，「直接失败」会让 CI 永远红 —— 打印跳过并写进文档是唯一诚实的选项 |
| **S5-D12** | `measure-startup.ps1` 新增 `-UserDataDir`（隔离 `EVEJS_USER_DATA_DIR`） | 不隔离时现役版会读**真实用户设置**，可能按用户偏好自动拉起主服务/市场服务，把服务进程算进「启动器内存」（本机实测出现过 1441 MB / 8 进程的脏数据）。两个外壳都认这个环境变量，跨外壳对比必须两边都带 |

### 4.3 L7 同口径重测（**推翻了旧结论**）

条件：同一台机器、同一个修正后的 `measure-startup.ps1`（启动 = CreateProcess → **按标题匹配的可见主窗口**；
内存 = 启动后 10 s / 60 s 对**整棵进程树** WorkingSet64 求和，CIM 精确父子关系），
两边都挂**同一个隔离 userdata**（`-UserDataDir .parity-out/measure-userdata`），各 3 轮：

| 外壳 | 启动(ms) 平均（min–max） | 内存@10s | 内存@60s | 进程数 |
| --- | --- | --- | --- | --- |
| Electron 现役 0.1.24（`release/win-unpacked`） | **963**（911–1046） | 445.7 MB | 445.8 MB | 6 |
| Tauri 0.2.0（`src-tauri/target/release`） | **1137**（1081–1205） | 430.1 MB | 417.7 MB | 7 |

结论（三条，按重要度）：

1. **热启动没有优势**：Tauri 比现役版慢约 174 ms（+18%），两者都在 1 秒量级。
   旧结论「Tauri 快 1.7×」是口径错误的产物 —— 修正前的脚本用 `Process.MainWindowHandle`，
   会先撞上单实例插件的隐藏窗口（标题 `com.evejs.launcher-siw`）。
2. **内存只低 6.3%**（417.7 vs 445.8 MB），量级完全在同一档。两个外壳都是 Chromium 内核在渲染
   **同一个 10.97 MB 的 legacy 页面**，换外壳不可能解决「内存极少」——这必须是 S6 的页面瘦身
   （`docs/baseline.md` §4：目标稳态 ≤150 MB）。
3. **冷启动本轮没有测**（需要重启机器或用工具清空 standby list 才能测准，本机不具备）。
   现役版冷启动 10.8 s 那一行口径有效（它没有单实例辅助窗口），而 Tauri 侧的 0.64 s **不可信**。
   可验证的假设：Tauri 便携版是「解压即用目录」，没有 Electron 首次启动解包 Chromium 的开销，
   冷启动应当明显更快 —— 但这需要一个真正的冷启动测量才能给数，已登记为债务（§7 #3）。

> 测量脚本自身的教训（S5-D12）：不隔离 userdata 时，现役版按真实用户设置自动拉起服务，

### 4.4 L7 冷启动的**交付前预检**（避免「白重启一次」）

上一轮把登录任务注册好就交还了。重启前做了一遍预检，结论是**按原样重启会一个数都拿不到** —— 全是「一次机会、失败无回执」的静默失败（预检累计 P1–P6）：

| # | 预检发现 | 真实后果 | 处置 |
| --- | --- | --- | --- |

### 4.5 L3 端到端沙箱（首个**写通道**场景）

L2 覆盖的 26 个通道全是只读的；L3 往下走一层，**真调写通道**。落地物：`tests/e2e/`，已接成 `scripts/build.ps1` 第 12 步（`-SkipE2E` 可关）。

沙箱口径（全文见 `tests/e2e/README.md`）：

- 仓库根 → `.parity-out/e2e-sandbox/repo`（cwd 的 `launcher.config.json` 指过去，复用 L2 的 `make-repo-fixture.mjs`）；
- 运行时目录 → `.parity-out/e2e-sandbox/userdata`（`EVEJS_USER_DATA_DIR`）；
- 快照 = 「相对路径 → 大小 + sha256」清单 + 一份副本；还原 = 整棵删掉再敷回去，digest 必须逐字节一致；
- **默认跑 2 轮**：第 2 轮完全建立在还原后的树上，两轮改动指纹必须一致 —— 同时证明「还原是逐字节的」与「沙箱能反复用」。

首个场景 `repo-mods`（10 步，全部在 `mods:*`，不联网、不需要 EveJS 服务端）：
`createFolder → create ×2 → list → setEnabled(true) → list → setOrder → plan → uninstall → list`。

实测（release 产物，2026-09-26）：

| 轮次 | 回包 | 用时 | 沙箱改动 | 断言 |
| --- | --- | --- | --- | --- |
| 1 | 10/10 | 3214 ms | 新增 5：`repo/mods/e2e-keep/{CHANGELOG.md,README.md,evejs-launcher.mod.json,loader.js}` + `userdata/mods/mod-order.json` | 60/60 |
| 2 | 10/10 | 3203 ms | 同上，**四个仓库文件哈希逐字节相同** | 60/60 |

断言不止「回包 ok」：盘上是 `loader.js`（而不是 `loader.js.disabled`）= 启用改名真生效；`repo/mods/e2e-gone` 不在 = 卸载真生效；两轮仓库产物哈希一致 = 场景确定性；还原 digest == 基线 digest = 可回滚；跑完无残留进程、四个端口全释放。

这一轮抓到的三条（细节见 `tests/e2e/README.md` §6）：

1. **启动器每次启动都会静默出网**拉市场索引（`ui/web/launcher-bridge.js` 末尾的 `void loadMarket(false, true)`，为页签徽章服务）。本机实测连**只读自检**都会生成 `userdata/cache/mod-index.json`，离线时要走满 12s 总预算。**不是移植缺陷**（现役版同款行为），但它是 E2E 不确定性的根源 —— 沙箱改为预置一份 30 分钟 TTL 内的缓存，并断言它没有被重写（重写即判定本轮出网、直接判失败）。
2. `launcher.config.json` 内容非法（尾部多一个字符）时，`env::read_launcher_config_repo_root` **静默返回 None**，仓库根一路回退到 **exe 所在目录** —— 启动器不报错，而是换个目录去建 `mods/`。本轮先登记（是否与现役版一致待后续场景确认）。
3. 自己踩的坑：配置文件末尾多一个**字面** `\\n` 会让 JSON 解析失败，于是整轮写操作落到 `src-tauri/target/debug/mods/`。教训是「沙箱一旦没生效，写通道会真写盘」—— 沙箱脚本自己必须有断言，不能靠人看。

## 10. L4–L8 收口（2026-09-26 续测）

### 10.1 L4 / L6 抓到的真缺陷：ConPTY 的光标查询必须被应答

`ESC[6n`（DSR：报告光标位置）是 ConPTY 启动时发的第一条数据，**子进程在收到应答前不吐任何输出**。
现役版之所以没暴露这个问题，是因为它的日志页挂着 xterm.js —— 终端仿真器会自动应答。
S6 的 React 日志页**刻意不带终端仿真**（省掉 xterm 的体积与每 tab 一份缓冲），于是：

- 修复前：L4 压测只收到 4 字节 `ESC[6n`，之后 120 s 一片空白（PID 有、输出没有，现场极难判断）；
- 修复后：`answer_terminal_queries()` 在 PTY 输出泵里应答 `ESC[1;1R`，10 万行 0 丢失。

**结论**：应答必须放在 PTY 这一层，不能依赖渲染层「有没有终端仿真器」。回归测试
`conpty_cursor_query_is_answered`（不需要真进程，毫秒级）已锁住这条。

### 10.2 L5：中文没问题，但 ConPTY 会「重新序列化」VT 流

实测口径（`scripts/check-encoding.ps1`，本机活动代码页 **936**）：

```
[L5] 活动代码页 936 · cmd 原文 "<ESC>[6n<ESC>[?9001h<ESC>[?1004h<ESC>[m<ESC>]0;C:\WINDOWS\system32\cmd.EXE BEL<ESC>[?25h中文测试·936"
     node 原文 "<ESC>[6n<ESC>[?9001h<ESC>[?1004h<ESC>[m<ESC>]0;C:\nodejs\node.EXE BEL<ESC>[?25h<ESC>[31m红色 <ESC>[m中文B"
```

三点结论：

1. **中文无乱码**：`中文测试·936`（含 GBK 专有的 `·`）逐字对上 —— 与现役版口径一致（现役版是 `d.toString()`，UTF-8）；
2. **ANSI 颜色未丢**：`ESC[31m` 原样到达；
3. ⚠️ **不是字节直通**：ConPTY 把子进程的 VT 流重新序列化了一遍 —— 复位从 `ESC[0m` 变成 `ESC[m`，
   并注入了会话头（`ESC[?9001h`、OSC 标题、光标显示）。渲染层必须能吃下这两种形态。

第 3 点连带在渲染层抓到**两个真缺陷**（现役版有 xterm.js 兜着，所以从没暴露）：

| 缺陷 | 后果 | 修法 |
| --- | --- | --- |
| `ansi.ts` 只剥 CSI，不剥 **OSC** | 日志页每行头都显示 `]0;C:\nodejs\node.EXE` 这种垃圾 | 加 `OSC_PATTERN`（到 BEL/ST 整条剥掉）+ `ESCAPE_TAIL` 兜底（任何不认识的转义都不许以裸 ESC 进 DOM） |
| `ESC[1m` 后接颜色码会把**加粗吃掉** | `ESC[1mESC[32m` 只剩绿色，加粗消失 | 修饰与颜色分开记账，flush 时再拼 className |

两个缺陷各配了 vitest 用例（`ui/src/lib/__tests__/ansi.test.ts`），并且第一个用例直接把 L5 抓到的
**真实字节**当固定向量。

### 10.3 L6：进程树是「按 PID 树」收的，必须真起两级才能证明

`win32.rs` 新增 Toolhelp32 探针（`snapshot_processes` / `descendants` / `alive`），

### 10.4 L8：本机升级/回滚演练（`scripts/release-drill.ps1`）

| 环节 | 做法 | 实测 |
| --- | --- | --- |
| 载荷 | 同一份源码编两个版本（当前版 + `patch+1`），跑完自动还原版本号并重建 | 0.2.0 → 0.2.1（debug 约 21 MB） |
| 清单 | `scripts/gen-drill-manifest.mjs` 用**演练固定密钥**签名（与 parity 向量同源），启动器用 `EVEJS_UPDATE_KEY_ID/PUBKEY` 覆盖验签；**内置公钥保持空 = fail closed 不动** | 验签 → `available=true` |
| 下载 | `EVEJS_UPDATE_MANIFEST_URL=file://…` + `EVEJS_UPDATE_ALLOW_LOCAL=1`，目标 `EVEJS_UPDATE_TARGET_PATH` 指向演练副本 | 下载产物 SHA256 与载荷逐字节一致 |
| 替换 + 重启 | 真跑 `vendor/updater` 的 Go 更新器；它带 `--updated`（**不带** `--self-test`）重启新版，因此演练不会自我循环 | 新版进程出现并存活 >3 s |
| 回滚 | 反向再推一次（清单版本 0.2.2 → 载荷 = 旧版字节），断言目标 exe 的 SHA256 回到旧版 | 6/6 通过 |

**演练的价值证明**：3 轮 × 2 方向里出现 **1 次偶发失败**（第 2 轮回滚：替换动作没落地）。
这类失败对用户是致命的（启动器等于坏了），而本地偶发 1/6 远高于 0.5% 的门槛。已按此加固更新器：

- `renameWithRetry`（`target→backup`、`new→target`，各 40 次 × 200 ms ≈ 8 s 预算）
- `copyWithRetry`（25 次 × 200 ms）

理由写进代码注释：被杀掉的旧进程刚释放镜像、或杀软正扫描新文件时，`os.Rename` 会拿到一次共享冲突；
**不该把一次瞬时冲突当成最终结果**。加固后用 Go 1.24.4 重编，复跑 6/6。

**仍未覆盖**：计划里「≥30 台次、成功率 ≥99.5%、真实灰度」需要发布通道与机器池，本机演练**不能**替代它 →
登记为 S7 发布前置条件（`docs/S7-发布与回滚-实施记录.md`）。

### 10.7 收口时被门禁抓到的两个「门禁自身」缺陷（2026-09-26）

把 L4/L5/L6/L8 接进 `build.ps1`（新增 `-SkipHeavy`）之后，**连跑两次全量门禁各红一次**，两次都不是产品代码的问题，
而是门禁/编排自己的缺陷 —— 这类「红灯来源不可信」比缺陷本身更危险，必须修在根上：

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| ① | L2 同实现自比随机红：`update:state` 字段变化（`state`, `message`） | dump 采集点撞上**瞬时态**：宿主渲染层首屏会主动 `update:check`，状态短暂为 `checking`（带 message「正在检查更新…」）。冻结基线当时正好把这个瞬时值写进去了，而同一个二进制再跑一次拿到的是 `idle` | **修在采集侧**：`ipc/smoke.rs` 的 dump 循环前等 `update:state` 落到非 `checking`（25 × 200 ms 上限，只影响 dump 模式）；随后用 `diff.mjs --update` 刷新被污染的那一条基线 |
| ② | L8 演练在第 3 轮起点抛 `文件正被另一进程使用`（`install\EvEJSLauncher.exe`），整条构建挂掉 | 与 §10.4 里更新器 `renameWithRetry` 遇到的是**同一类瞬时共享冲突**（上一轮刚被杀掉的进程还没释放镜像文件映射 / 杀软正在扫描新写入的 exe），但演练编排脚本自己的复位复制没有重试 | `release-drill.ps1` 加 `Stop-StrayLaunchers` + `Wait-UpdaterIdle`（先清场）+ `Set-InstallPayload`（25 × 200 ms 重试，重试耗尽时打印仍存活的嫌疑进程）+ `Get-Sha256` 容忍瞬时占用 |

补充说明 ①：`diff-cross.mjs` 的豁免表里**本来就有** `update:state` 的三键豁免，理由正是这个不对称
（Electron harness 不加载渲染层 → 一直 `idle`）；**同实现自比没有豁免**，所以只能在采集侧把瞬时态消掉。
刷新后的基线值是 `{"currentVersion":"0.2.0","state":"idle"}`，与 Electron 侧口径一致。

### 10.8 第三个「门禁自身」缺陷：A4 的 `pageCspClean` 曾经**恒定失败**

跑真机自检时才暴露：两个入口（`--ui=react` 默认入口与 `--ui=legacy`）都报 `pageCspClean = False`，
而页面本身并没有违规 —— 问题出在**断言自己的时序**：

| 环节 | 原实现 | 后果 |
| --- | --- | --- |
| 注册「页面违规」监听 | 在**等渲染层挂载之后** | 挂载期与首屏副作用的违规全被漏掉 |
| 摘除该监听 | 在**故意注入的探针之后** | 探针自己那条 `script-src` 违规被算进「页面自身违规」 |

两头都错 ⇒ 这条断言**永远为假**（等于没有门禁，而且把红灯指向了错误的方向）。
修法：监听器提前到「等挂载」之前注册、探针注入**之前**摘掉并结算，中间补 400 ms 静默期收挂载后的异步副作用；
同时把违规的指令名带进结果（`summary.pageCspViolations`）并在 `smoke-ipc.ps1` 打印 —— 红灯必须自证。

**修完实测**：`--ui=react` 与 `--ui=legacy` 各跑一次，A4 九条断言全绿、26/26 通道有回包（两条命令都 exit 0）。
这也顺带说明 React 首屏（含 shadcn 组件、懒加载 iframe、懒 fetch）确实**零 CSP 违规**，是可信的正面证据。

同一轮还顺手清掉三个小项：

- `cargo clippy --all-targets -- -D warnings` 在 L5 测试里抓到 `filter(...).next_back()`（`clippy::filter_next`）→ 改 `rfind(..)`；
- `scripts/*.ps1` 统一补 UTF-8 BOM（`build.ps1` / `release-drill.ps1` / `package.ps1` / `smoke-webview2-missing.ps1` 四份缺 BOM，
  与 §4.4 抓到的「5.1 按 GBK 解析中文」是同一类坑）；
- CI 的 `build.ps1` 调用加 `-SkipHeavy`：L4/L5/L6/L8 需要交互桌面会话与 Go 工具链，属**发布前**门禁（见 `docs/S7-发布与回滚-实施记录.md` §5.2）。

**复跑证据**：`pwsh -File scripts/build.ps1` 1–17 步全绿（含 L3 60 项断言、L4 10 万行 0 丢失、L5 代码页 936、
L6 停服 0 残留、L8 6/6，升级 apply 7.8–8.3 s / 回滚 7.8–8.3 s）。
