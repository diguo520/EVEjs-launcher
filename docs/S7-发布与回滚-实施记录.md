## 2. 双轨 manifest（A5）

### 2.1 真实冲突（本轮查证，**必须先解决再发布**）

现役 Electron 0.1.28 的默认清单地址（`.../launcher/dist/main/main/updater.js:49`）与新外壳**完全相同**：

```
https://github.com/diguo520/EVEjs-launcher/releases/latest/download/update-manifest.json
```

两边都从 `releases/latest` 取清单，而且**旧版的更新流程不认识 zip**：

| 环节 | 旧版（Electron 0.1.28）行为 | 与新清单相遇的后果 |
| --- | --- | --- |
| 资产选择 | `platforms["win32-x64"]`（`updater.js:115`） | 字段同名，**会选中**新通道的 zip |
| 校验 | 只核 `sha256`（`updater.js:238`），**不验签** | zip 的 sha256 是对的 → 校验通过 |
| 落盘 | 存成 `launcher-<version>.exe`（`updater.js:236`） | 一个 `.zip` 被当成 exe |
| 替换 | Go 更新器把该文件换到 `--target` 指向的 exe（`updater.js:277`） | **现役用户的主程序被替换成 zip 字节 → 启动器报废** |

结论：**Tauri 便携 zip 绝不能发布到 `releases/latest`**（这是「静默毁用户」级的事故，不是体验问题）。

### 2.2 双轨设计（三选一，推荐 #2）

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| #1 第二仓库 | 新通道 manifest 放 `EVEjs-launcher-v2`，改 `updater.rs:26` 的 `DEFAULT_MANIFEST_URL` | 需维护者建仓库 + 改常量（一次性） |
| **#2 固定 tag（推荐）** | 新通道读 `.../releases/download/stable/update-manifest.json`；发布脚本把 `stable` tag 移到新 release；旧版继续读 `releases/latest`（永久停在 Electron 停机页包） | 改一次常量 + 发布脚本多一条「移动 tag」 |
| #3 env/settings 覆盖 | 新通道地址经 `settings.updateManifestUrl` 下发 | ❌ 便携版用户拿不到初始值，不成立 |

**为什么 #2 可行**：清单地址优先级是 `EVEJS_UPDATE_MANIFEST_URL` → `settings.updateManifestUrl` →
`launcher.config.json.updateManifestUrl` → 内置默认（`updater.rs:6-7`、`manifest_url_from()`），
所以只要把**内置默认**从 `latest` 换成 `stable` tag，新旧两个通道就互不打扰，且不依赖新仓库。

  `EvEJSLauncher.exe` 与 `msedgewebview2.exe`（本机无 ETL 采集器，属 §6-① 的一部分）。

## 4. 回滚演练（本机，已完成）

脚本 `scripts/release-drill.ps1`：**同一份源码编两个版本**（当前版 + `patch+1`，跑完自动还原版本号并重建）
→ `scripts/gen-drill-manifest.mjs` 用演练固定密钥签名清单 → `file://` + `EVEJS_UPDATE_ALLOW_LOCAL=1`
→ 真跑 `vendor/updater` 的 Go 更新器替换 exe → 观测新版进程出现并存活 >3 s → 反向再推一次完成回滚。
内置公钥保持空（fail closed 不动），全程用 `EVEJS_UPDATE_KEY_ID/PUBKEY/TARGET_PATH` 覆盖。

实测（2026-09-26，`.parity-out/release-drill.json`）：

| 项 | 结果 |
| --- | --- |
| 方向 | 3 轮 × 2 方向 = **6/6 通过**，成功率 100%（两次独立复跑均为 6/6） |
| 升级 apply | 约 7.8–8.3 s（debug 载荷约 21 MB） |
| 回滚 apply | 约 7.8–8.3 s |
| 验签 | 通过（演练密钥） |
| 载荷一致性 | 下载产物 SHA256 与载荷**逐字节一致** |
| 重启存活 | 新版进程存活 >3 s（带 `--updated`，不带 `--self-test`，不会自我循环） |

**演练的价值证明**：首轮 3 轮 × 2 方向里出现 **1 次偶发失败**（第 2 轮回滚替换没落地，1/6 ≈ 17%，
远高于 0.5% 门槛）。已据此加固更新器：`renameWithRetry`（40 次 × 200 ms）与 `copyWithRetry`（25 次 × 200 ms）
—— 旧进程刚释放镜像、或杀软正在扫描新文件时 `os.Rename` 会拿到一次共享冲突，**不该把一次瞬时冲突当最终结果**。
加固后复跑 6/6。失败时脚本自动保留现场（`-KeepWork`）并抓 `TMP/EveJS-Launcher-Updater/updater.log`。

**第二次加固（演练编排侧）**：把 L8 接进 `build.ps1` 后，第 3 轮起点抛出「`install\EvEJSLauncher.exe`
正被另一进程使用」—— 这是**编排脚本自己的复位复制**没有重试，与更新器遇到的是同一类瞬时共享冲突
（刚被杀掉的进程还没释放镜像文件映射 / 杀软在扫描新写入的 exe）。已加：`Stop-StrayLaunchers` +
`Wait-UpdaterIdle`（每轮先清场）、`Set-InstallPayload`（25 × 200 ms 重试，耗尽时打印仍存活的嫌疑进程）、
`Get-Sha256` 容忍瞬时占用。**教训**：演练脚本也是被测链路的一部分，它的「红灯」必须可信。

复跑命令：

```powershell
pwsh -File scripts/release-drill.ps1                 # 3 轮 × 2 方向
pwsh -File scripts/release-drill.ps1 -Rounds 1       # 快速自检
pwsh -File scripts/release-drill.ps1 -Configuration release
```

**仍未覆盖**：真实灰度机器上的回滚、回滚包的签名分发、`--updated` 重启后的服务自动拉起（需真仓库 fixture）。
