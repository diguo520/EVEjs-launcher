## 3. 本轮修掉的真 bug（都在真机上复现过）

1. **React 渲染层整页白屏**：`env-check.tsx` 的「正在检测 X」用 `items[Math.min(done, items.length - 1)].name`，
   真自检起步时 `items` 是空的 → 取到 `undefined` → 渲染期抛错 → React 卸载整棵树。
   已改为「没有项就不画进度条」并加 `?.name ?? ""`。同时把自检面板顶部那行写死的
   「Node v26.5.0 · 32 GB RAM · 16 线程」换成 `env:check` 的真值（Node 版本 / 内存 / 线程数）。
2. **状态栏 `PING [object Object] ms`**：`health:ping` 回的是 `{ok, port, ms}`，原来直接 `String(reply)`。
   现在取 `ms`（端口没人监听时 `ms` 为 null → 画 `—`，不写 `— ms`）。
3. **配置中心端口与原型不符**：原型写的是 3001 / 8080，真实是 26001 / 26002（`config:get`）；
   服务端三个端口与两处来源路径**启动器没有写通道**，因此改成只读展示（原型画成可编辑会误导）。

## 8. 老启动器用户零重置接管（身份 key / GitHub 令牌）

用户最在意的一点：已经在用老（Electron）启动器的人换到新框架后，**不用重新生成身份 key、不用重填 GitHub 令牌**。
做法分两条腿，互相兜底：

**腿 1 — 路径语义逐行对齐（`src-tauri/src/runtime.rs`）**：新启动器的 `_launcher/data` 与老版**同一套规则**。
所以只要把新 exe 解压进老启动器目录（或老目录旁），两边天然共用同一份 `_launcher/data`，什么都不用做。
（`author:openKeyFolder` 打开 `_launcher/data`，与老版 `authorDataDir()` 行为一致。）

**腿 2 — 首次接管（`src-tauri/src/legacy.rs`）**：新启动器被放到**别处**、本机 `_launcher/data` 还是空的时候，
启动时从老目录**首次搬一份**过来。规则是「宁可少做，也不要错认」：

| 条目 | 来源 | 说明 |
| --- | --- | --- |
| `author.json` | 老 `_launcher/data/author.json` | 只在目标不存在时搬；`id` / `keyId` / `publicKey` / `since` 原样保留 |
| `mod-keys/<keyId>.key` | `author.json.privateKeyPath`（相对路径） | 老版写的是明文 PKCS#8 PEM，新版能直接读；`mod-keys/*.key` 全目录一并兜底带上 |
| `github-token.bin` | 老 `_launcher/data/github-token.bin` | OSCrypt（`v10…`）密文**原样搬字节**；解密它的 AES 密钥在隔壁 `cache/Local State`，一并搬（见下） |
| `launcher-settings.json:accountCredentials` | 老设置文件 | **只补 `accountCredentials` 这一项**，不覆盖新启动器已有设置 |

- 任一目标文件已存在就绝不覆盖；`EVEJS_USER_DATA_DIR`（隔离 / 测试模式）生效时完全不接管。
- 结果落在 `_launcher/data/legacy-adoption.json`，并挂到 `app:info.legacy` 给设置页显示（`legacy-panel.tsx`）。
- 老启动器那份数据**只读不写**，随时可以退回老版。

### 实测证据（探针 `.parity-out/tools/adopt-probe3.ps1`）

在假 repo + 预置老数据（真 Node 生成的 Ed25519 PKCS#8 PEM 私钥 + DPAPI 加密令牌）下、**不设** `EVEJS_USER_DATA_DIR` 启动自检：

- `app:info.legacy` → `{adopted: true, items: ["author.json","mod-keys/4d2eda93729c.key","github-token.bin","launcher-settings.json:accountCredentials"]}`
- `author:get` → `id` / `keyId` / `publicKey` / `since` 与老数据**逐字段一致**，`privateKeyExists: true`（老版明文 PEM 直接可用）
- `mods:githubTokenStatus` → `hasToken: true, encrypted: true`
- `settings:get` → `{accountCredentials:{veteran:"enc-secret"}}`（只搬凭据，其余设置不动）
- 老目录文件**字节数不变**（可整份回退）

> 排查留痕：更早一次探针报 `privateKeyExists:false`，逐层核对后确认是**探针自己**把假 key 内容写成了非 PEM 的乱码
> （`decode_key_file` 自然解不开），**不是代码 bug**；换成真 PEM 后立即为 `true`。已补单测
> `author::tests::legacy_forward_slash_key_path_is_readable`，锁死「正斜杠 / 反斜杠相对路径都要能定位私钥」。

### 为什么不能只搬字节：Electron `safeStorage` **不是**裸 DPAPI

老版令牌 / 账号密码落盘走 Electron `safeStorage`，那是 **Chromium OSCrypt**，不是一次 `CryptProtectData`：

| | 形态 |
| --- | --- |
| 老版 `github-token.bin`（真机实测，明文 24 字节） | **56 字节**，头部 ASCII `v10` |
| 裸 DPAPI 对同样明文 | **246 字节**（`01 00 00 00 D0 8C …`） |

密文结构：`v10 | nonce(12) | AES-256-GCM 密文 | tag(16)`；那把 AES-256 密钥本身再用 DPAPI 包一层，
base64 后落在 Chromium 的 `Local State` 里（键 `os_crypt.encrypted_key`，前缀 `DPAPI` 5 字节）。

> 结论是**真机验出来的**：直接调老启动器编译产物 `saveToken('ghp_legacy_real_token_zzz')`
> （`githubToken.js` + `authorStore.js` + `PORTABLE_EXECUTABLE_DIR` 模拟便携版），拿到真密文后
> 用 Node `crypto.createDecipheriv('aes-256-gcm', key, nonce)` **严格解出了明文**，格式与上面完全一致。

**密钥文件的位置**：老启动器 `src/main/index.ts:19-24` 把 `sessionData` 指到 `<运行时根>/cache`，
Electron 33 的 OSCrypt 密钥正好落在 `sessionData/Local State`。受控实验（改 `APPDATA` + 只调 `app.setPath`）确认：

| 退出方式 | `<root>/cache/Local State` |
| --- | --- |
| `app.exit(0)`（强杀） | **不落盘** |
| `app.quit()`（优雅退出） | **434 字节，写下来** |

所以真机上那份密钥在 `<老目录>/_launcher/cache/Local State` —— 本机四个老目录
（`launcher/launcher/`、`launcher/launcher/release/`、`launcher/launcher/release/win-unpacked/`、根目录）
下都躺着一份 434 字节的 `cache/Local State`，而不是我们第一版以为的裸 DPAPI blob。

**新启动器怎么接**（`src-tauri/src/oscrypt.rs`，手写 bcrypt.dll / CNG FFI 实现 AES-256-GCM）：

1. `legacy::adopt` 搬 `github-token.bin` 时，**顺手把隔壁 `cache/Local State` 里的 AES 密钥也搬过来**
   （`store_key` → `<data>/os-crypt-key.bin`，同样用 DPAPI 包一层），接管清单里记一笔
   `cache/Local State:os_crypt.encrypted_key`；
2. 候选密钥按 `os-crypt-key.bin` → 本机 `cache/Local State` → `<data>/Local State` 依次收集，
   解密时逐把试（GCM 的 tag 校验保证试错不会误判）；
3. 一把都找不到就**现生成一把**并落盘，绝不退回裸 DPAPI，也绝不静默返明文；
4. 解密端两种格式都认：`v10` 开头走 AES-256-GCM，其余按裸 DPAPI 解（我们更早一版自己写过的格式）。

| lottie | `lottie_light.min-*.js` 167.6 KB + 数据 14.4 KB | 1,248.6 KB |
| webm | 无（视频是嵌入资产，424 KB） | 1,247.7 KB |

CSP 里没有单列 `media-src`，会退回 `default-src 'self'` —— 所以 WebM 只能随包，不能外链、也不能用 `data:`。

### 18.2 踩到的坑：`?url` 导入不看 tree-shaking

最初 webm 写的是 `import url from "@/assets/boot/boot.webm?url"`，结果 **424 KB 的视频进了全部五个包**：
Vite 的资产模块在 `load` 阶段就 `emitFile`，不看这个模块最后有没有被折掉。
改成运行时相对路径 `./boot.webm`，由打包脚本按变体注入 `ui/dist/react/boot.webm`。
Tauri 把 `frontendDist` 整棵树嵌进 exe，所以这份视频现在是**嵌在 exe 里**的，目录里不放散件。

### 18.3 四个变体各是什么

- **canvas**（`boot/boot-canvas-fx.tsx`）：0 依赖。星点粒子 + 绕 Logo 的两段速度弧 + 一圈扫描环。
  `devicePixelRatio` 封顶 2、密度按面积算、`prefers-reduced-motion` 时只画一帧静态画面。
- **three**（`boot/boot-three-fx.tsx`）：正交相机按**像素坐标**摆（`left/right/top/bottom` = 视口边缘），
  `Points` 星场 + 三段 `RingGeometry` 弧。环几何只在测量 / resize 时重建，逐帧只动 transform 与 opacity。
  先自己探一次 WebGL 上下文，拿不到就静默不渲染、退回 CSS 层。
- **lottie**（`boot/boot-lottie-fx.tsx` + 生成的 `boot/boot-fx-lottie-data.ts`）：light 播放器（只带 SVG 渲染器）。
  容器是**贴着 Logo 的 360 px 定尺寸方框**，720 的画布用 `meet` 装进去 —— 倍率恒为 0.5，与窗口尺寸无关。
  （最初按 `slice` 铺满全屏，1400×900 下 720 的画布被放大 1.94 倍，半径 292 的弧直接冲出画面。）
- **webm**（`boot/boot-webm-fx.tsx`）：ffmpeg 离线合成的 6 s 无缝循环（星点上浮 + 两条扫描线）。
  底色取 `#0B1120`（`--background` 的平色，不是渐变：VP9 压深色平滑渐变必出阶梯条带，已实测），
  中心环境光交给本来就存在的 CSS `.mission-glow`。

五个变体都保留 `.boot-orbit` / `.mc-pulse` / 信号带 / 文字；`prefers-reduced-motion` 下都不动。

### 18.4 资产怎么生成

`scripts/make-boot-assets.mjs`（离线、可重复、不需要联网）：

- Lottie 数据 → `ui/src/components/shell/boot/boot-fx-lottie-data.ts`（18.7 KB / 20 层：3 段弧 + 16 颗星）。
  做成 `.ts` 模块而不是 `.json`：进 `src` 才会被打包器当模块处理（也省掉 `resolveJsonModule` 与运行时 fetch）。
- WebM → `ui/assets/boot.webm`（424 KB，1280×720 / 30 fps / 6 s）。
  星点用 `drawbox` 的表达式逐帧算位置，速度取 `736×k/6` px/s，保证首尾接得上；CRF 26 + 极淡时域抖动压块。
  ffmpeg 不在 PATH 时会跳过这一半并给出提示。
